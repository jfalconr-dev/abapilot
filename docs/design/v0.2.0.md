# Resumen ejecutivo

Este documento describe el diseño funcional y arquitectónico de la versión **v0.2.0** de ABAPilot.

Su finalidad es proporcionar una visión común del alcance de la versión, del modelo de dominio, de la arquitectura de la solución y de las principales decisiones que guiarán su implementación.

No pretende sustituir la documentación técnica detallada ni la especificación de la API. Su propósito es definir qué se va a construir, cómo se organiza la solución y qué principios deberán respetarse durante el desarrollo.

# 3. Alcance funcional

## 3.1 Propósito

Este capítulo define las capacidades incluidas en la versión **v0.2.0** de ABAPilot y delimita el alcance funcional de esta primera entrega.

La versión prioriza la consolidación de una arquitectura estable frente a la incorporación temprana de un gran número de funcionalidades, sentando las bases para la evolución del producto en versiones posteriores.

---

## 3.2 Funcionalidades incluidas

La versión **v0.2.0** ofrece una primera experiencia orientada a profesionales del ecosistema SAP, tanto funcionales como técnicos.

### Asistencia al profesional SAP

El sistema permite formular consultas relacionadas con los procesos de negocio, la implantación, el desarrollo y el mantenimiento de soluciones SAP, proporcionando respuestas generadas mediante un proveedor de inteligencia artificial.

Esta capacidad constituye el principal punto de interacción entre el usuario y ABAPilot.

### Explicación de código ABAP

ABAPilot analiza fragmentos de código ABAP y genera explicaciones orientadas a facilitar su comprensión.

Esta capacidad resulta especialmente útil durante tareas de mantenimiento, la incorporación de nuevos desarrolladores o el análisis de desarrollos existentes.

### Revisión de código

El sistema revisa desarrollos ABAP desde una perspectiva cualitativa, identificando oportunidades de mejora relacionadas con la legibilidad, la mantenibilidad y la aplicación de buenas prácticas de desarrollo.

Las recomendaciones generadas tienen carácter informativo y no modifican automáticamente el código analizado.

---

## 3.3 Capacidades previstas para versiones futuras

Las siguientes capacidades no forman parte del alcance de la versión **v0.2.0**. No obstante, la arquitectura se diseña teniendo en cuenta su incorporación progresiva en futuras versiones.

- integración con distintos proveedores de inteligencia artificial configurables en tiempo de ejecución
- persistencia del historial de conversaciones
- gestión de usuarios y autenticación
- personalización del comportamiento del asistente mediante perfiles de configuración
- análisis de proyectos completos en lugar de fragmentos de código
- incorporación de bases de conocimiento especializadas mediante técnicas de recuperación de información (RAG)
- integración con herramientas del ecosistema SAP
- incorporación de una interfaz de usuario web

La exclusión de estas capacidades responde a la voluntad de mantener un alcance controlado para la primera versión del producto, sin comprometer su evolución futura.

# 4. Modelo de dominio

## 4.1 Propósito

Este capítulo describe los conceptos fundamentales que forman parte del dominio de ABAPilot y las relaciones existentes entre ellos.

El modelo de dominio representa la forma en que el producto interpreta las necesidades de los profesionales del ecosistema SAP, con independencia de las tecnologías utilizadas para implementar la solución.

---

## 4.2 Visión del dominio

ABAPilot se concibe como un espacio de trabajo asistido para profesionales del ecosistema SAP.

Su finalidad es ayudar a comprender, analizar y resolver necesidades relacionadas con los procesos de negocio, la implantación, el desarrollo y el mantenimiento de soluciones SAP.

Desde la perspectiva del dominio, el funcionamiento interno del sistema, los modelos de inteligencia artificial utilizados y la infraestructura tecnológica empleada carecen de relevancia.

El dominio únicamente contempla aquellos conceptos que representan la interacción entre el profesional SAP y el conocimiento que necesita para desempeñar su trabajo.

Por este motivo, conceptos propios de la implementación, como los proveedores de inteligencia artificial, los modelos de lenguaje o las técnicas de procesamiento, no forman parte del modelo de dominio y se describen en capítulos posteriores dedicados a la arquitectura de la solución.

---

## 4.3 Conceptos principales

El modelo de dominio de ABAPilot se articula alrededor de cinco conceptos fundamentales.

Estos conceptos representan los elementos necesarios para describir la interacción entre un profesional del ecosistema SAP y el conocimiento que el sistema pone a su disposición.

Cada uno de ellos posee una responsabilidad claramente definida y permanece independiente de las tecnologías empleadas para implementar la solución.

### Profesional SAP

Representa a la persona que utiliza ABAPilot para obtener apoyo durante el desempeño de su actividad.

Desde la perspectiva del dominio, no se establecen diferencias entre perfiles funcionales y técnicos. Todos ellos interactúan con el sistema mediante el mismo modelo conceptual, formulando consultas o proporcionando código ABAP para su análisis.

El profesional SAP constituye el origen de toda interacción con el sistema.

### Consulta

Representa la necesidad de información expresada por un profesional SAP.

Una consulta puede estar relacionada con procesos de negocio, implantación, desarrollo, mantenimiento o cualquier otra actividad propia del ecosistema SAP.

La consulta constituye el mecanismo mediante el cual el profesional comunica al sistema la necesidad de información que desea resolver.

### Código ABAP

Representa el fragmento de código ABAP que un profesional proporciona al sistema para solicitar su explicación o revisión.

El código ABAP constituye la entrada principal de las capacidades relacionadas con el análisis de código y se diferencia del contexto adicional que puede acompañar a la solicitud.

Desde la perspectiva del dominio, este concepto representa únicamente el contenido que debe analizarse, con independencia del origen del código o del mecanismo utilizado para enviarlo al sistema.

### Contexto

Representa la información adicional que acompaña a una consulta o a un fragmento de código ABAP y permite interpretarlos con mayor precisión.

El contexto puede estar formado por descripciones funcionales, mensajes de error, características del sistema SAP, objetivos del análisis o cualquier otro elemento relevante para comprender la necesidad planteada.

Su finalidad es complementar la entrada principal de la interacción y facilitar una respuesta más adecuada.

### Respuesta

Representa el conocimiento proporcionado por ABAPilot para ayudar al profesional SAP a comprender, analizar o resolver la necesidad planteada.

La respuesta puede incluir explicaciones, recomendaciones, propuestas de mejora o cualquier otra información útil para el usuario.

Desde la perspectiva del dominio, la respuesta constituye el resultado de la interacción entre el profesional SAP y el sistema, con independencia del mecanismo utilizado para generarla.

---

## 4.4 Relaciones entre conceptos

Los conceptos que forman el modelo de dominio representan las distintas etapas de una misma interacción entre un profesional SAP y ABAPilot.

Toda interacción comienza cuando un profesional SAP plantea una consulta relacionada con una necesidad surgida durante el desempeño de su actividad.

La consulta puede complementarse con un contexto que aporte información adicional y facilite su correcta interpretación. Este contexto no constituye una consulta independiente, sino un elemento que enriquece y precisa la información proporcionada por el usuario.

Como resultado del análisis de la consulta y de su contexto, ABAPilot proporciona una respuesta orientada a ayudar al profesional SAP a comprender, analizar o resolver la necesidad planteada.

Desde la perspectiva del dominio, esta secuencia representa una única interacción lógica. Los mecanismos utilizados para interpretar la consulta, procesar el contexto o generar la respuesta pertenecen a la arquitectura del sistema y quedan fuera del modelo de dominio.

---

## 4.5 Responsabilidades del dominio

Cada concepto del modelo de dominio posee una responsabilidad claramente definida dentro de la interacción entre el profesional SAP y ABAPilot.

El profesional SAP representa el origen de toda interacción con el sistema y constituye el destinatario del conocimiento proporcionado por ABAPilot.

La consulta expresa la necesidad que el usuario desea resolver y actúa como elemento central de la interacción.

El contexto aporta la información necesaria para interpretar correctamente la consulta y mejorar la calidad de la respuesta generada.

La respuesta representa el conocimiento que ABAPilot pone a disposición del profesional SAP para ayudarle a comprender, analizar o resolver la necesidad planteada.

La combinación de estas responsabilidades permite construir un modelo de dominio sencillo, cohesionado e independiente de las tecnologías utilizadas para implementar la solución.

# 5. Arquitectura lógica

## 5.1 Propósito

Este capítulo describe la organización lógica de ABAPilot y la distribución de responsabilidades entre los principales componentes que forman la solución.

La arquitectura propuesta tiene como objetivo dar soporte al modelo de dominio descrito en el capítulo anterior, manteniendo una clara separación entre las reglas del negocio y los aspectos relacionados con la infraestructura y las tecnologías utilizadas para implementar el sistema.

---

## 5.2 Visión general

ABAPilot adopta una arquitectura organizada por responsabilidades, donde cada componente desempeña una responsabilidad claramente definida y colabora con el resto mediante contratos bien definidos.

Esta organización permite mantener el dominio independiente de las decisiones tecnológicas y facilita la evolución del producto sin introducir cambios significativos en su núcleo funcional.

La arquitectura persigue los siguientes objetivos:

- preservar la independencia del modelo de dominio
- reducir el acoplamiento entre componentes
- facilitar la incorporación de nuevas capacidades
- simplificar las pruebas automatizadas
- favorecer la mantenibilidad y la evolución del sistema

---

## 5.3 Organización de la arquitectura

Desde un punto de vista conceptual, la arquitectura de ABAPilot puede entenderse como una sucesión de responsabilidades que conducen desde el punto de entrada del sistema hasta su núcleo funcional.

```text
Cliente
    │
    ▼
API REST
    │
    ▼
Aplicación
    │
    ▼
Dominio
```

El recorrido comienza en la API REST, responsable de recibir las solicitudes realizadas por los clientes y transformarlas en operaciones comprensibles para la aplicación.

La capa de Aplicación coordina la ejecución de los distintos casos de uso y actúa como punto de unión entre el modelo de dominio y el resto de capacidades del sistema.

El Dominio constituye el núcleo de ABAPilot y representa los conceptos y reglas del negocio definidos en el capítulo anterior. Ningún elemento perteneciente al dominio depende de tecnologías concretas ni de componentes de infraestructura.

Esta organización permite comprender el sistema de forma progresiva, avanzando desde los mecanismos de interacción externos hasta el modelo conceptual que representa el negocio.

---

## 5.4 Colaboración entre componentes

Aunque el recorrido conceptual concluye en el dominio, la ejecución de los distintos casos de uso requiere la colaboración con componentes encargados de proporcionar capacidades técnicas.

Estas capacidades forman parte de la infraestructura del sistema e incluyen, entre otras, el acceso a proveedores de inteligencia artificial, mecanismos de persistencia y futuras integraciones con sistemas externos.

La coordinación de estas colaboraciones corresponde exclusivamente a la capa de Aplicación.

El modelo de dominio permanece completamente ajeno a la existencia de dichos componentes y no mantiene dependencias directas con ellos.

Esta separación permite sustituir tecnologías, incorporar nuevas integraciones o modificar la infraestructura sin afectar a las reglas del negocio ni al modelo de dominio de ABAPilot.

---

## 5.5 Componentes arquitectónicos

La arquitectura de ABAPilot se organiza en cuatro componentes principales, cada uno de ellos con una responsabilidad claramente delimitada.

Esta separación permite mantener un bajo acoplamiento entre las distintas partes del sistema y facilita su evolución sin comprometer la estabilidad del modelo de dominio.

### API REST

La API REST constituye el punto de entrada de ABAPilot.

Su responsabilidad consiste en recibir las solicitudes realizadas por los clientes, validar la información recibida y transformarla en operaciones que puedan ser procesadas por la capa de Aplicación.

La API REST no implementa reglas de negocio ni coordina el funcionamiento del sistema más allá del tratamiento propio de la comunicación con el exterior.

### Aplicación

La capa de Aplicación coordina la ejecución de los distintos casos de uso del sistema.

Su responsabilidad consiste en orquestar la interacción entre el modelo de dominio y los componentes de infraestructura necesarios para resolver cada operación.

La Aplicación representa el punto de unión entre el negocio y las capacidades técnicas utilizadas por ABAPilot, evitando que ambos ámbitos dependan directamente entre sí.

### Dominio

El Dominio constituye el núcleo funcional del producto.

Contiene los conceptos, responsabilidades y reglas que representan la forma en que ABAPilot interpreta las necesidades de los profesionales del ecosistema SAP.

El Dominio permanece completamente independiente de cualquier decisión tecnológica y no mantiene dependencias con componentes de infraestructura.

### Infraestructura

La Infraestructura proporciona las capacidades técnicas necesarias para que la Aplicación pueda ejecutar los distintos casos de uso.

Entre otras responsabilidades, incluye la comunicación con proveedores de inteligencia artificial, mecanismos de persistencia, servicios externos e integraciones con otros sistemas.

La Infraestructura implementa las dependencias técnicas del sistema sin introducir reglas de negocio propias.

---

## 5.6 Dependencias entre componentes

La arquitectura de ABAPilot establece una dirección única para las dependencias entre sus componentes.

Cada componente únicamente puede depender de aquellos cuya responsabilidad resulte necesaria para desempeñar su propia función, evitando dependencias innecesarias o circulares.

Las dependencias entre componentes se rigen por las siguientes reglas:

- La API REST depende exclusivamente de la capa de Aplicación.
- La capa de Aplicación depende del Dominio y de abstracciones que representan las capacidades técnicas necesarias para ejecutar los distintos casos de uso.
- La Infraestructura implementa dichas abstracciones y proporciona el acceso a los recursos técnicos del sistema.
- El Dominio no depende de ningún otro componente de la solución.

Como consecuencia de estas reglas, las decisiones relacionadas con tecnologías, proveedores o mecanismos de comunicación permanecen aisladas del modelo de dominio y pueden evolucionar sin afectar a las reglas del negocio.

---

## 5.7 Principios arquitectónicos

La arquitectura de ABAPilot se fundamenta en un conjunto reducido de principios cuyo objetivo es preservar la estabilidad del producto y facilitar su evolución.

### Independencia del dominio

El modelo de dominio constituye el núcleo funcional de ABAPilot y no mantiene dependencias con tecnologías, proveedores o mecanismos de infraestructura.

Toda capacidad técnica necesaria para ejecutar los distintos casos de uso se incorpora mediante componentes externos al dominio, preservando la estabilidad de las reglas del negocio.

### Separación de responsabilidades

Cada componente de la arquitectura asume una responsabilidad claramente definida.

La distribución de responsabilidades evita duplicidades, reduce el acoplamiento entre componentes y facilita la evolución independiente de cada parte del sistema.

### Sustituibilidad tecnológica

La arquitectura se diseña para permitir la sustitución de componentes tecnológicos sin modificar el modelo de dominio.

La incorporación de nuevos proveedores de inteligencia artificial, mecanismos de persistencia o integraciones externas debe realizarse sin alterar las reglas del negocio representadas por el dominio.

### Evolución incremental

La incorporación de nuevas funcionalidades debe realizarse mediante la extensión de los componentes existentes o la incorporación de nuevos componentes, evitando modificaciones innecesarias sobre el núcleo del sistema.

Este principio favorece la mantenibilidad y reduce el riesgo asociado a la evolución del producto.

---

## 5.8 Decisiones arquitectónicas

Las principales decisiones adoptadas durante el diseño de ABAPilot responden a la necesidad de construir una arquitectura sencilla, mantenible y preparada para evolucionar de forma incremental.

Cada decisión persigue preservar la independencia del modelo de dominio y minimizar el impacto que las futuras modificaciones puedan tener sobre el resto del sistema.

Las decisiones fundamentales son:

- mantener el dominio completamente independiente de cualquier tecnología concreta
- incorporar las capacidades técnicas mediante abstracciones claramente definidas
- asignar una única responsabilidad a cada componente arquitectónico
- favorecer la evolución incremental del producto sin comprometer la estabilidad del núcleo funcional

# 6. Diseño de la API REST

## 6.1 Propósito

La API REST constituye el punto de entrada mediante el cual las aplicaciones cliente interactúan con ABAPilot.

Su diseño tiene como objetivo proporcionar una interfaz sencilla, coherente y desacoplada de la implementación interna del sistema. De este modo, las capacidades del producto pueden consumirse mediante contratos estables sin exponer la organización de los casos de uso ni las tecnologías empleadas para acceder a los proveedores de inteligencia artificial.

La API representa la única vía de acceso a las funcionalidades incluidas en la versión **v0.2.0** y ofrece, además, una operación técnica para comprobar el estado del servicio.

Este capítulo describe los principios que guían el diseño de la API, los recursos y operaciones disponibles, el modelo de intercambio de datos y el tratamiento aplicado a los errores.

---

## 6.2 Principios de diseño

La API REST de ABAPilot se diseña con el objetivo de proporcionar una interfaz consistente, sencilla de utilizar y preparada para evolucionar sin afectar innecesariamente a las aplicaciones cliente.

Las decisiones adoptadas mantienen un desacoplamiento claro entre la interfaz pública del sistema y la implementación interna de los casos de uso.

Para ello, la API se fundamenta en los siguientes principios.

### Orientación a recursos

La API organiza sus capacidades mediante recursos que representan los principales servicios ofrecidos por ABAPilot.

Los recursos funcionales se agrupan bajo la ruta `/assistant`, mientras que las operaciones técnicas se exponen de forma independiente. Esta organización permite distinguir las capacidades destinadas a los usuarios de aquellas relacionadas con el funcionamiento del servicio.

### Consistencia

Las operaciones funcionales mantienen criterios uniformes en cuanto a nomenclatura, formato de las peticiones, estructura de las respuestas y tratamiento de los errores.

Todas ellas reciben datos en formato JSON y devuelven el resultado generado mediante una propiedad común denominada `response`.

### Independencia de la implementación

Los contratos de la API permanecen independientes de la organización interna de la aplicación y del proveedor de inteligencia artificial utilizado.

Las aplicaciones cliente no necesitan conocer qué proveedor procesa una solicitud ni cómo se organizan internamente los casos de uso. Esto permite modificar o sustituir componentes internos sin alterar el contrato público de la API.

### Evolución compatible

La incorporación de nuevas capacidades deberá preservar, siempre que sea posible, la compatibilidad con los contratos existentes.

Los cambios que amplíen una petición o una respuesta deberán diseñarse de forma que no obliguen a modificar inmediatamente las aplicaciones cliente ya integradas.

---

| `/assistant/review`  | Funcional | Revisar código ABAP e identificar oportunidades de mejora relacionadas con su calidad y mantenibilidad.               |

## 6.4 Operaciones disponibles

Los recursos funcionales utilizan el método HTTP `POST` porque reciben la información que debe procesarse en el cuerpo de la petición y generan un resultado específico para cada solicitud.

El recurso técnico utiliza el método `GET`, ya que permite consultar el estado del servicio sin proporcionar un cuerpo de petición ni modificar el estado del sistema.

| URI del recurso      | Método HTTP | Descripción                                                                        |
| -------------------- | ----------- | ---------------------------------------------------------------------------------- |
| `/health`            | `GET`       | Devuelve la identificación, versión y estado actual de la API.                     |
| `/assistant/query`   | `POST`      | Procesa una consulta relacionada con el ecosistema SAP y genera una respuesta.     |
| `/assistant/explain` | `POST`      | Analiza un fragmento de código ABAP y genera una explicación de su funcionamiento. |
| `/assistant/review`  | `POST`      | Analiza un fragmento de código ABAP e identifica oportunidades de mejora.          |

Cada operación representa un contrato independiente. La incorporación futura de nuevas capacidades podrá realizarse mediante nuevos recursos sin modificar los contratos existentes.

## 6.5 Modelo de intercambio de datos

### Formato de intercambio

La API utiliza JSON como formato para representar los datos intercambiados con las aplicaciones cliente.

Las peticiones dirigidas a los recursos funcionales deben enviar su contenido como JSON. Las respuestas satisfactorias y las respuestas de error también se representan mediante este formato.

### Consulta al asistente

La operación `POST /assistant/query` recibe una consulta relacionada con SAP.

| Campo     | Tipo   | Obligatorio | Tratamiento                                                                  |
| --------- | ------ | ----------- | ---------------------------------------------------------------------------- |
| `query`   | Cadena | Sí          | Debe contener texto distinto de espacios en blanco.                          |
| `context` | Cadena | No          | Si contiene texto válido, se utiliza como información adicional de contexto. |

Ejemplo de petición:

```json
{
  "query": "¿Cuál es la finalidad de una orden de transporte en SAP?",
  "context": "La consulta se refiere a un sistema SAP ECC."
}
```

### Explicación de código ABAP

La operación `POST /assistant/explain` recibe el fragmento de código que debe explicarse.

| Campo     | Tipo   | Obligatorio | Tratamiento                                                                  |
| --------- | ------ | ----------- | ---------------------------------------------------------------------------- |
| `code`    | Cadena | Sí          | Debe contener código distinto de espacios en blanco.                         |
| `context` | Cadena | No          | Si contiene texto válido, se utiliza como información adicional de contexto. |

Ejemplo de petición:

```json
{
  "code": "SELECT * FROM mara INTO TABLE lt_mara UP TO 10 ROWS.",
  "context": "Explicar el fragmento a un desarrollador ABAP principiante."
}
```

### Revisión de código ABAP

La operación `POST /assistant/review` utiliza la misma estructura de petición que la operación de explicación.

| Campo     | Tipo   | Obligatorio | Tratamiento                                                                  |
| --------- | ------ | ----------- | ---------------------------------------------------------------------------- |
| `code`    | Cadena | Sí          | Debe contener código distinto de espacios en blanco.                         |
| `context` | Cadena | No          | Si contiene texto válido, se utiliza como información adicional de contexto. |

Ejemplo de petición:

```json
{
  "code": "SELECT * FROM mara INTO TABLE lt_mara.",
  "context": "Revisar la legibilidad, mantenibilidad y aplicación de buenas prácticas."
}
```

### Normalización y validación de las peticiones

La API elimina los espacios situados al principio y al final de los campos de texto antes de ejecutar el caso de uso correspondiente.

Los campos principales `query` y `code` se consideran inválidos cuando:

- no están presentes en la petición;
- no son cadenas de texto;
- contienen únicamente espacios en blanco.

En cualquiera de estos casos, la API rechaza la solicitud y devuelve una respuesta con el código HTTP `400`.

El campo `context` es opcional. Cuando no es una cadena de texto válida o contiene únicamente espacios en blanco, la API lo ignora y procesa la petición sin información adicional de contexto.

### Respuestas funcionales satisfactorias

Las tres operaciones funcionales utilizan la misma estructura de respuesta:

```json
{
  "response": "Resultado generado por ABAPilot."
}
```

La propiedad `response` contiene el texto generado para la consulta, explicación o revisión solicitada.

Cuando la operación se completa correctamente, la API devuelve el código HTTP `200`.

### Respuesta del recurso de estado

La operación `GET /health` devuelve una estructura con la identificación del servicio, su versión actual y su estado:

```json
{
  "service": "abapilot-api",
  "version": "0.1.0",
  "status": "ok"
}
```

El valor de `version` corresponde a la versión publicada de la API y deberá actualizarse durante el proceso de cierre de cada versión del producto. El valor `0.1.0` refleja el estado del servicio durante el desarrollo de la versión **v0.2.0**.

Cuando el servicio está disponible, esta operación devuelve el código HTTP `200`.

---

## 6.6 Tratamiento de errores

La API proporciona un mecanismo uniforme para comunicar las situaciones en las que una solicitud no puede completarse correctamente.

Las respuestas de error utilizan la siguiente estructura general:

```json
{
  "error": "Descripción del error."
}
```

Los códigos HTTP contemplados por la versión **v0.2.0** son los siguientes:

| Código HTTP | Situación                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------- |
| `200`       | La solicitud se ha procesado correctamente.                                                 |
| `400`       | La petición no contiene un valor válido para el campo principal requerido por la operación. |
| `500`       | Se ha producido un error interno durante el procesamiento de la solicitud.                  |

Los errores de validación informan a la aplicación cliente de que la petición no cumple el contrato esperado.

Los errores internos se transforman en una respuesta genérica. La API no expone excepciones, configuraciones, datos del proveedor de inteligencia artificial ni otros detalles internos que puedan revelar información sobre la implementación.

Este tratamiento centralizado mantiene un comportamiento homogéneo entre los distintos recursos y evita que cada operación establezca su propio formato de error.

## 6.7 Evolución de la API

La API de ABAPilot se diseña para evolucionar de forma incremental, permitiendo incorporar nuevas capacidades funcionales sin alterar, siempre que sea posible, los contratos ya publicados.

La incorporación de nuevos recursos o campos opcionales deberá preservar la compatibilidad con las aplicaciones cliente existentes. Del mismo modo, los cambios internos relacionados con los casos de uso o los proveedores de inteligencia artificial no deberán repercutir en el contrato público mientras no modifiquen el comportamiento funcional comprometido.

Las modificaciones incompatibles con versiones anteriores deberán abordarse mediante una nueva versión de la API y una estrategia de transición que permita preservar temporalmente los contratos existentes cuando resulte necesario.

La evolución de la API deberá mantener la coherencia con el modelo de dominio, la arquitectura lógica y las restricciones arquitectónicas definidas en este documento.
