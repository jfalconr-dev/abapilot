# 1. Introducción

## 1.1 Propósito del documento

Este documento define el diseño funcional y técnico de ABAPCompass v0.3.0.

La versión v0.3.0 evoluciona la base establecida en v0.2.0 incorporando
una primera interfaz web orientada al usuario, un mecanismo de selección
dinámica del modelo de inteligencia artificial y medidas adicionales
para favorecer un uso controlado y responsable de las respuestas
generadas.

El documento constituye la referencia arquitectónica para la implementación
de la versión v0.3.0. Su objetivo es establecer las responsabilidades de
los distintos componentes, los contratos entre capas, el comportamiento
esperado de la API REST, el diseño de la interfaz web y los criterios de
validación de la versión.

La implementación deberá respetar las decisiones recogidas en este
documento. Cuando durante el desarrollo resulte necesario introducir una
modificación significativa respecto al diseño previsto, esta deberá
justificarse y reflejarse en la documentación para mantenerla alineada
con la solución implementada.

## 1.2 Contexto y punto de partida

ABAPCompass es un asistente especializado orientado a profesionales SAP,
diseñado para facilitar tareas de consulta, comprensión y revisión
técnica mediante el uso de modelos de inteligencia artificial.

La versión v0.2.0 estableció una arquitectura modular capaz de ofrecer
las siguientes operaciones:

- responder consultas relacionadas con SAP.
- explicar código ABAP.
- revisar código ABAP.

Estas capacidades se encuentran disponibles mediante una API REST y
utilizan la abstracción `AIProvider`, que desacopla los casos de uso de
la tecnología concreta empleada para proporcionar las capacidades de
inteligencia artificial.

Como primera implementación de esta abstracción, ABAPCompass integra Ollama
para permitir la ejecución local de modelos de lenguaje. La arquitectura
permite incorporar en futuras versiones otros proveedores de
inteligencia artificial, tanto locales como remotos, sin modificar los
casos de uso de la aplicación.

La versión v0.2.0 también introdujo políticas de generación de código
asociadas a las capacidades del modelo, diferenciando entre los modos
`none`, `snippets` y `full`.

Hasta v0.2.0, la utilización de ABAPCompass requiere interactuar
directamente con la API REST mediante herramientas técnicas. Además, el
proveedor y el modelo utilizados se determinan de forma global durante
el arranque de la aplicación.

La versión v0.3.0 parte de esta base estable para proporcionar una
interfaz orientada al usuario y permitir la selección dinámica del
modelo utilizado en cada operación, preservando el desacoplamiento entre
los casos de uso, los modelos y los proveedores de inteligencia
artificial.

## 1.3 Objetivos de la versión

El objetivo principal de ABAPCompass v0.3.0 es proporcionar una primera
experiencia completa de interacción orientada al usuario manteniendo la
separación entre presentación, aplicación, dominio e infraestructura.

Los objetivos específicos son:

1. Incorporar una interfaz web desde la que puedan utilizarse las tres
   capacidades existentes de ABAPCompass.
2. Permitir al usuario seleccionar el modelo de IA utilizado por las
   operaciones realizadas desde la interfaz.
3. Proporcionar un catálogo controlado de modelos soportados por
   ABAPCompass.
4. Asociar a cada modelo una política de generación de código definida
   por la aplicación.
5. Resolver dinámicamente el proveedor y modelo correspondiente a cada
   petición sin acoplar los casos de uso a Ollama ni a modelos
   concretos.
6. Incorporar en todas las respuestas satisfactorias un aviso explícito
   que recuerde la necesidad de revisión profesional y validación
   previa antes de aplicar una solución en entornos productivos.
7. Mantener la API REST como punto de entrada común a las capacidades
   de ABAPCompass, evitando que la interfaz web acceda directamente a
   componentes internos o al proveedor de IA.
8. Ampliar la cobertura de pruebas y el pipeline de integración
   continua para incluir las nuevas funcionalidades.

## 1.4 Alcance

ABAPCompass v0.3.0 incluirá:

- una aplicación web desarrollada con Vite, TypeScript y HTML/CSS
  nativos.
- una interfaz orientada a las capacidades disponibles.
- una interfaz para consultas SAP.
- una interfaz para explicación de código ABAP.
- una interfaz para revisión de código ABAP.
- consulta del catálogo de modelos soportados.
- selección del modelo utilizado en las operaciones.
- mantenimiento de la selección del modelo mientras se utiliza la
  interfaz.
- un modelo seleccionado inicialmente por defecto.
- visualización de las capacidades de generación de código del modelo
  seleccionado.
- aplicación de las políticas `none`, `snippets` y `full`, combinando
  instrucciones preventivas al modelo con controles deterministas
  cuando corresponda.
- resolución dinámica del `AIProvider`.
- trazabilidad del modelo utilizado en las respuestas.
- un aviso de validación profesional en las respuestas satisfactorias.
- gestión de estados de carga y error en la interfaz web.
- pruebas unitarias, de integración, API y las validaciones aplicables
  a la interfaz web.
- integración de las nuevas validaciones en el proceso de CI.

## 1.5 Fuera de alcance

Quedan expresamente fuera del alcance de v0.3.0:

- autenticación y gestión de usuarios.
- autorización y gestión de roles.
- persistencia de conversaciones.
- historial de consultas.
- persistencia de preferencias de usuario entre sesiones.
- integración RAG con documentación.
- bases de datos vectoriales.
- conexión directa con sistemas SAP.
- ejecución automática de código ABAP.
- despliegue de cambios en sistemas SAP.
- administración o descarga de modelos de IA desde la interfaz.
- detección automática de los modelos instalados localmente.
- configuración dinámica del catálogo mediante base de datos o
  interfaz de administración.
- despliegue en un entorno productivo.

Estas capacidades podrán evaluarse en versiones posteriores, pero no
deberán introducirse durante la implementación de v0.3.0 salvo que una
necesidad técnica imprescindible obligue a reconsiderar el alcance.

# 2. Requisitos funcionales

Este capítulo define el comportamiento funcional que deberá proporcionar
ABAPCompass v0.3.0. Los requisitos descritos se consideran independientes
de los detalles concretos de implementación, que se desarrollarán en
capítulos posteriores.

## 2.1 Interfaz web

ABAPCompass v0.3.0 deberá proporcionar una interfaz web que constituya el
principal medio de interacción del usuario con las capacidades de la
aplicación.

La interfaz deberá permitir acceder de forma diferenciada a las tres
capacidades funcionales existentes:

- realizar consultas relacionadas con SAP.
- explicar código ABAP.
- revisar código ABAP.

La interfaz web actuará como consumidor de la API REST de ABAPCompass y no
accederá directamente a los casos de uso, a los proveedores de
inteligencia artificial ni a los modelos utilizados.

El usuario deberá poder completar las operaciones habituales sin
necesidad de utilizar herramientas técnicas para realizar peticiones
HTTP directamente contra la API.

La interfaz deberá informar claramente del estado de cada operación,
diferenciando al menos entre:

- operación preparada para su ejecución.
- operación en curso.
- operación completada correctamente.
- operación finalizada con error.

## 2.2 Asistente SAP

La interfaz deberá permitir al usuario formular una consulta relacionada
con SAP.

La operación deberá admitir:

- una consulta obligatoria.
- contexto adicional opcional.
- identificación del modelo de IA seleccionado.

Una vez enviada la petición, ABAPCompass deberá procesarla utilizando el
modelo seleccionado y presentar al usuario la respuesta obtenida.

Una respuesta satisfactoria deberá identificar el modelo utilizado,
informar de la política de generación de código aplicada e incluir el
aviso de validación profesional definido por ABAPCompass.

El contenido generado por el modelo deberá considerarse información no
verificada y no implicará que ABAPCompass garantice su corrección técnica.

## 2.3 Explicación de código ABAP

La interfaz deberá permitir introducir un fragmento de código ABAP para
solicitar una explicación de su funcionamiento.

La operación deberá admitir:

- código ABAP obligatorio.
- contexto adicional opcional.
- identificación del modelo de IA seleccionado.

ABAPCompass deberá enviar el código al modelo seleccionado aplicando las
reglas y políticas correspondientes a la operación de explicación.

Una respuesta satisfactoria deberá presentar la explicación generada,
identificar el modelo utilizado, informar de la política de generación
de código aplicada e incluir el aviso de validación profesional.

ABAPCompass no ejecutará ni compilará el código recibido como parte de esta
operación.

La explicación generada deberá considerarse contenido no verificado y no
equivaldrá a una validación técnica realizada mediante herramientas SAP.

## 2.4 Revisión de código ABAP

La interfaz deberá permitir introducir código ABAP para solicitar su
revisión.

La operación deberá admitir:

- código ABAP obligatorio.
- contexto adicional opcional.
- identificación del modelo de IA seleccionado.

La revisión podrá incluir observaciones relacionadas con legibilidad,
mantenibilidad, posibles defectos, rendimiento y buenas prácticas, en
función de la información disponible para el modelo.

Las observaciones producidas deberán considerarse recomendaciones y no
resultados equivalentes a una validación mediante compilación, análisis
estático o ejecución real del código.

Una respuesta satisfactoria deberá identificar el modelo utilizado,
informar de la política de generación de código aplicada e incluir el
aviso de validación profesional.

ABAPCompass no modificará ni ejecutará automáticamente el código analizado.

## 2.5 Catálogo de modelos de IA

ABAPCompass deberá mantener un catálogo explícito de modelos de IA
soportados.

El catálogo constituirá la lista autorizada de modelos que pueden
utilizarse mediante la aplicación.

Cada modelo deberá disponer, como mínimo, de:

- un identificador único dentro de ABAPCompass.
- un nombre destinado a su presentación al usuario.
- una descripción de su orientación o finalidad.
- una política de generación de código.

El catálogo previsto para la versión estará formado por:

| Orientación         | Modelo                | Política de generación de código |
| ------------------- | --------------------- | -------------------------------- |
| Uso general         | Llama 3.2 3B          | `none`                           |
| Desarrollo asistido | Qwen 2.5 Coder 7B     | `snippets`                       |
| Desarrollo avanzado | DeepSeek Coder V2 16B | `full`                           |

La orientación indicada tiene carácter descriptivo y facilita al usuario
la elección del modelo. No constituye un atributo independiente que
determine el comportamiento de ABAPCompass.

La política de generación de código será el atributo que determine
formalmente el nivel de generación permitido para cada modelo.

La pertenencia de un modelo al catálogo indica que ABAPCompass reconoce su
configuración y política asociada. No constituye una certificación sobre
la exactitud de sus respuestas ni sobre su conocimiento de SAP o ABAP.

Los modelos no incluidos en el catálogo deberán considerarse no
soportados.

## 2.6 Selección de modelo

La interfaz web deberá permitir al usuario seleccionar el modelo de IA
que se utilizará para ejecutar las operaciones.

La selección deberá estar limitada a los modelos incluidos en el
catálogo de ABAPCompass.

La interfaz deberá proporcionar información suficiente para distinguir
los modelos disponibles, conocer su orientación y conocer su política de
generación de código antes de realizar una operación.

El usuario seleccionará el modelo, pero no podrá modificar de forma
independiente la política de generación de código asociada a este.

La interfaz web presentará inicialmente un modelo predeterminado
definido por ABAPCompass.

La selección realizada por el usuario se mantendrá mientras utilice la
interfaz y será común a las distintas capacidades de ABAPCompass hasta que
el usuario seleccione otro modelo.

La selección mantenida por la interfaz no modificará la configuración
global del backend ni requerirá que este conserve estado sobre la
elección realizada por el usuario.

Cada petición dirigida a una capacidad de ABAPCompass deberá identificar
explícitamente el modelo seleccionado.

Si una petición no especifica un modelo o el identificador recibido no
corresponde a un modelo soportado, la operación deberá ser rechazada de
forma controlada.

## 2.7 Políticas de generación de código

ABAPCompass asociará a cada modelo soportado una política que determine el
nivel de generación de código permitido.

Se establecen tres políticas:

- `none`: se solicitará al modelo que la respuesta no proporcione código.
- `snippets`: se permitirá al modelo proporcionar fragmentos de código
  limitados cuando resulten necesarios para apoyar la explicación o
  recomendación.
- `full`: se permitirá al modelo proporcionar soluciones de código
  completas cuando resulten justificadas por la consulta.

La política será determinada por ABAPCompass a partir del modelo
seleccionado y no podrá ser alterada directamente por el usuario.

Las denominaciones técnicas `none`, `snippets` y `full` podrán
representarse en la interfaz mediante textos más comprensibles:

- `none`: No genera código.
- `snippets`: Fragmentos de código.
- `full`: Soluciones completas.

ABAPCompass aplicará la política correspondiente mediante instrucciones
preventivas proporcionadas al modelo antes de generar la respuesta.

Debido a la naturaleza no determinista de los modelos de lenguaje, estas
instrucciones no constituyen por sí mismas una garantía absoluta de
cumplimiento.

Para la política `none`, ABAPCompass incorporará además un control
determinista sobre la respuesta generada. Cuando se detecten bloques de
código delimitados, estos serán omitidos de la respuesta presentada al
usuario, manteniéndose el resto del contenido generado.

ABAPCompass aplicará este filtrado únicamente a bloques de código claramente
delimitados en la respuesta. No intentará detectar como código fragmentos
incluidos por el modelo dentro del texto normal de la respuesta.

La respuesta de la API proporcionará información que permita conocer si
se ha aplicado este filtrado. La interfaz utilizará esta información para
indicar visualmente, en la posición correspondiente, que un bloque de
código ha sido omitido debido a la política configurada.

Las políticas `snippets` y `full` establecerán el comportamiento
solicitado al modelo, pero no implicarán que el código generado sea
correcto, compilable, seguro o adecuado para un sistema SAP concreto.

Toda salida generada por un modelo de inteligencia artificial se
considerará contenido no confiable. ABAPCompass no ejecutará código ni
acciones propuestas en las respuestas generadas por los modelos.

Cualquier código generado deberá estar sujeto a revisión y validación
profesional antes de su utilización.

## 2.8 Aviso de validación profesional

Toda respuesta satisfactoria generada mediante las capacidades de
asistencia SAP, explicación ABAP o revisión ABAP deberá incorporar un
aviso de validación profesional.

El aviso será generado de forma determinista por ABAPCompass y no deberá
depender del contenido producido por el modelo de inteligencia
artificial.

El texto definido para v0.3.0 será:

> **Validación profesional requerida**
>
> Esta respuesta ha sido generada por IA y puede contener errores,
> omisiones o suposiciones incorrectas. Verifica la información antes de
> utilizarla. No ejecutes las acciones propuestas ni utilices el código
> generado directamente en entornos productivos sin una revisión técnica
> previa.

El aviso formará parte de la respuesta proporcionada por ABAPCompass
mediante la API REST y no dependerá de la interfaz web para su
incorporación.

La interfaz web deberá mostrarlo de forma claramente visible junto al
resultado de una operación satisfactoria.

El aviso no implica que ABAPCompass realice automáticamente ninguna
validación técnica de la respuesta. Su finalidad es informar de que las
respuestas generadas por modelos de inteligencia artificial pueden
contener errores, omisiones o suposiciones incorrectas y requieren
revisión profesional antes de utilizar su contenido, ejecutar las
acciones propuestas o emplear código generado en un entorno productivo.

# 3. Requisitos no funcionales

Los requisitos no funcionales establecen los atributos de calidad y las
restricciones técnicas que deberán guiar el diseño y la implementación
de ABAPCompass v0.3.0.

La incorporación de una interfaz web y de la selección dinámica de
modelos no deberá comprometer los principios de modularidad,
mantenibilidad y desacoplamiento establecidos en versiones anteriores.

## 3.1 Arquitectura y mantenibilidad

ABAPCompass deberá mantener una arquitectura modular con separación clara
de responsabilidades entre presentación, aplicación, dominio e
infraestructura.

Los casos de uso no deberán depender de proveedores ni de modelos de
inteligencia artificial concretos.

La incorporación de nuevos proveedores o modelos deberá poder realizarse
mediante extensiones de los mecanismos definidos para este propósito,
evitando modificaciones innecesarias en los casos de uso existentes.

La interfaz web deberá permanecer desacoplada de la implementación
interna del backend y utilizar exclusivamente los contratos públicos
proporcionados por la API REST.

El código deberá mantener tipado estático mediante TypeScript y respetar
las reglas de formato, análisis estático y compilación definidas para el
proyecto.

Las nuevas funcionalidades deberán integrarse en la estructura existente
del repositorio evitando duplicación de responsabilidades y dependencias
innecesarias.

## 3.2 Seguridad

ABAPCompass deberá tratar cualquier información introducida por el usuario
como entrada no confiable.

Las entradas recibidas mediante la API deberán ser validadas antes de
ser procesadas por los casos de uso.

La selección de modelos estará limitada al catálogo de modelos
expresamente soportados por ABAPCompass. No deberá ser posible utilizar
identificadores arbitrarios recibidos mediante la API para acceder a
modelos no autorizados.

La interfaz web no deberá contener credenciales, claves de API, secretos
ni información sensible necesaria para acceder a proveedores de
inteligencia artificial.

Las credenciales que puedan requerir futuros proveedores deberán
mantenerse exclusivamente en el backend y obtenerse mediante mecanismos
de configuración externos al código fuente.

Los mensajes de error proporcionados mediante la API no deberán revelar
información sensible sobre la configuración interna, credenciales, rutas
locales o detalles innecesarios de la infraestructura.

Toda salida generada por un modelo de inteligencia artificial deberá
considerarse contenido no confiable.

ABAPCompass no ejecutará automáticamente código proporcionado por el
usuario, código generado por un modelo de inteligencia artificial ni
acciones propuestas en las respuestas generadas.

La interfaz web deberá tratar como no confiable el contenido procedente
tanto del usuario como de los modelos de inteligencia artificial y
representarlo de forma que no pueda ser interpretado como HTML
ejecutable.

## 3.3 Rendimiento

La incorporación de la interfaz web y del mecanismo de selección
dinámica de modelos no deberá introducir procesamiento innecesario en
las operaciones del backend.

Los componentes utilizados para resolver proveedores y modelos deberán
evitar inicializaciones o procesamiento innecesarios en cada petición.

El tiempo total de respuesta de las operaciones que utilizan
inteligencia artificial dependerá principalmente del proveedor, del
modelo seleccionado y de los recursos disponibles en el entorno de
ejecución. ABAPCompass deberá mantener la interfaz en un estado consistente
durante estas operaciones e informar al usuario mientras una petición
permanezca en curso.

La aplicación deberá gestionar tiempos de espera y fallos de
comunicación con los proveedores de inteligencia artificial sin bloquear
indefinidamente una operación.

No se establece para v0.3.0 un tiempo máximo de generación común a todos
los modelos, debido a las diferencias de tamaño, características y
entorno de ejecución existentes entre ellos.

## 3.4 Usabilidad y accesibilidad

La interfaz web deberá proporcionar una navegación sencilla y coherente
entre las capacidades de ABAPCompass.

Las acciones principales deberán poder identificarse sin necesidad de
conocer la estructura técnica de la aplicación ni los contratos de la
API REST.

La selección del modelo deberá mostrar información comprensible sobre su
orientación y sobre la política de generación de código asociada.

Los estados de carga, éxito y error deberán distinguirse claramente.

El aviso de validación profesional deberá mostrarse asociado a las
respuestas satisfactorias sin quedar oculto ni depender de acciones
adicionales del usuario para consultarlo.

Los formularios deberán identificar claramente los campos obligatorios y
opcionales y proporcionar mensajes comprensibles cuando los datos
introducidos no sean válidos.

La interfaz deberá poder utilizarse mediante teclado para las
operaciones principales y emplear elementos HTML semánticos siempre que
resulte posible.

El diseño deberá adaptarse razonablemente a diferentes tamaños de
pantalla, priorizando su utilización en equipos de escritorio sin
impedir su uso básico en dispositivos con pantallas de menor tamaño.

## 3.5 Observabilidad y tratamiento de errores

ABAPCompass deberá gestionar de forma controlada los errores producidos
durante la validación de las peticiones, resolución de modelos,
ejecución de los casos de uso y comunicación con proveedores externos.

Los errores deberán clasificarse de forma que la API pueda proporcionar
una respuesta adecuada sin exponer detalles internos innecesarios.

La aplicación deberá diferenciar, al menos, entre errores provocados por
una petición no válida, selección de un modelo no soportado,
indisponibilidad del proveedor, expiración del tiempo de espera y
errores internos inesperados.

Los eventos relevantes para el diagnóstico técnico deberán poder
registrarse en el backend.

Los registros no deberán incluir credenciales ni otros secretos de
configuración.

Cuando resulte necesario registrar información introducida por el
usuario, deberá evitarse almacenar contenido completo si no es
imprescindible para el diagnóstico.

La interfaz web deberá transformar los errores recibidos de la API en
mensajes comprensibles para el usuario, evitando mostrar directamente
trazas de excepción o información interna del backend.

## 3.6 Compatibilidad y portabilidad

ABAPCompass deberá mantener la separación entre la aplicación y los
proveedores concretos de inteligencia artificial para facilitar la
incorporación futura de alternativas locales o remotas.

La implementación de v0.3.0 utilizará Ollama como proveedor disponible
inicialmente, sin convertirlo en una dependencia conceptual de los casos
de uso ni de la interfaz web.

La aplicación deberá continuar siendo ejecutable en un entorno de
desarrollo local mediante las herramientas y procedimientos documentados
en el proyecto.

Los parámetros dependientes del entorno de ejecución, como direcciones
de servicios, puertos o tiempos de espera, deberán configurarse
externamente y no incorporarse directamente al código fuente.

La interfaz web y la API deberán disponer de comandos documentados y
reproducibles para su ejecución, compilación y validación automatizada.

La incorporación de la interfaz web no deberá modificar el carácter
público de los contratos de la API REST. Las capacidades de ABAPCompass
deberán continuar siendo accesibles mediante dicha API
independientemente de la interfaz web.

# 4. Arquitectura de la solución

La arquitectura de ABAPCompass v0.3.0 evoluciona la establecida en v0.2.0
sin modificar sus principios fundamentales de modularidad, separación de
responsabilidades y dependencia mediante abstracciones.

La principal evolución arquitectónica consiste en sustituir la selección
global de un único modelo durante el arranque por una resolución
dinámica del modelo y proveedor necesarios para cada operación.

La incorporación de la interfaz web proporciona un nuevo medio de
interacción con ABAPCompass. La interfaz se comunicará con el backend
exclusivamente mediante la API REST, sin acceder directamente a los
casos de uso ni a las implementaciones de los proveedores de
inteligencia artificial.

La aplicación de las políticas de generación de código combinará
instrucciones preventivas dirigidas al modelo con controles
deterministas sobre la respuesta cuando la política aplicable así lo
requiera.

## 4.1 Arquitectura general

ABAPCompass mantendrá una arquitectura modular organizada conceptualmente
en las siguientes áreas:

- presentación.
- aplicación.
- dominio.
- puertos.
- infraestructura.

La interfaz web y la API REST pertenecen al ámbito de presentación. La
API constituirá el punto de entrada al backend para las operaciones
realizadas desde la interfaz web.

La capa de aplicación coordinará los casos de uso y la selección de los
recursos de inteligencia artificial necesarios para ejecutarlos.

El dominio continuará representando los conceptos propios de las
operaciones de ABAPCompass sin depender de tecnologías de presentación,
proveedores de inteligencia artificial ni modelos concretos.

Los puertos definirán los contratos necesarios para desacoplar la lógica
de aplicación de las implementaciones de infraestructura.

La infraestructura proporcionará las implementaciones concretas
necesarias para acceder a los proveedores de inteligencia artificial.

La API aplicará además las políticas de respuesta necesarias antes de
exponer al consumidor el contenido generado por los modelos.

## 4.2 Principios de diseño

La evolución arquitectónica de v0.3.0 se regirá por los siguientes
principios:

- los casos de uso dependerán de abstracciones y no de proveedores
  concretos.
- la interfaz web dependerá exclusivamente de los contratos públicos
  de la API REST.
- cada petición dirigida a una capacidad de ABAPCompass identificará
  explícitamente el modelo que deberá utilizarse.
- el catálogo de modelos constituirá la fuente de verdad sobre los
  modelos soportados por ABAPCompass.
- cada modelo tendrá asociada una configuración y una política de
  generación de código controladas por ABAPCompass.
- las peticiones a la API podrán seleccionar únicamente modelos
  incluidos en el catálogo de ABAPCompass y no podrán determinar
  directamente el proveedor, la política de generación ni otras
  configuraciones internas.
- la incorporación futura de nuevos modelos deberá requerir cambios
  localizados.
- la incorporación futura de nuevos proveedores deberá realizarse
  mediante nuevas implementaciones de los puertos correspondientes,
  evitando modificar los casos de uso.
- las responsabilidades de catálogo, resolución, ejecución y aplicación
  de políticas permanecerán separadas.
- las decisiones específicas de infraestructura no deberán propagarse
  a las capas internas de la aplicación.
- toda salida generada por un modelo de inteligencia artificial se
  considerará contenido no confiable.
- ABAPCompass no ejecutará código ni acciones propuestas en las respuestas
  generadas por los modelos.

La dependencia entre componentes deberá orientarse hacia las
abstracciones internas de ABAPCompass y no hacia las tecnologías utilizadas
para implementarlas.

## 4.3 ModelCatalog

`ModelCatalog` será responsable de representar el conjunto de modelos de
inteligencia artificial soportados por ABAPCompass.

El catálogo actuará como una lista autorizada de modelos y constituirá
la fuente de verdad utilizada por la aplicación para conocer sus
características.

Cada modelo soportado estará representado mediante una definición que
incluirá la información necesaria para identificarlo, presentarlo al
usuario, resolver el proveedor encargado de ejecutarlo y aplicar la
política de generación de código correspondiente.

La estructura detallada de esta definición se especifica en el apartado
5.1.

`ModelCatalog` deberá proporcionar, al menos, las operaciones necesarias
para:

- obtener el conjunto de modelos soportados.
- localizar la definición correspondiente a un identificador de modelo.

Un modelo que no forme parte del catálogo se considerará no soportado
por ABAPCompass.

El catálogo de v0.3.0 será estático. La administración dinámica de
modelos no forma parte del alcance de esta versión.

## 4.4 AIProviderResolver

`AIProviderResolver` será responsable de obtener el `AIProvider`
apropiado para ejecutar una operación a partir del modelo seleccionado.

`AIProviderResolver` utilizará la definición del modelo que reciba para
determinar qué implementación de `AIProvider` debe utilizarse para
ejecutar la operación solicitada.

El proceso de resolución puede representarse conceptualmente de la
siguiente forma:

```text
ModelDefinition
      |
      +-- providerId
      +-- providerModel
              |
              v
     AIProviderResolver
              |
              v
         AIProvider
```

`AIProviderResolver` recibirá una definición de modelo previamente
obtenida de `ModelCatalog`. Si dicha definición referencia un proveedor
que no pueda ser resuelto por ABAPCompass, deberá producirse un error
controlado.

El identificador público recibido mediante la API no se utilizará
directamente para intentar acceder a un modelo de ningún proveedor.

`AIProviderResolver` no contendrá lógica propia de los casos de uso ni
decidirá qué política de generación debe asignarse a un modelo. Esa
información procederá de la definición existente en el catálogo.

La abstracción deberá permitir que futuras versiones incorporen
proveedores adicionales sin modificar el comportamiento de los casos de
uso.

## 4.5 AIProvider

`AIProvider` continuará siendo el puerto mediante el cual las
capacidades de ABAPCompass acceden a un proveedor de inteligencia
artificial.

Los casos de uso no deberán conocer si la implementación concreta
utiliza un modelo local, un servicio remoto o cualquier otra tecnología
compatible con el contrato.

Las implementaciones de `AIProvider` serán responsables de traducir las
operaciones definidas por ABAPCompass al mecanismo requerido por el
proveedor correspondiente.

En v0.3.0, Ollama continuará siendo el proveedor implementado para la
ejecución local de los modelos incluidos en el catálogo.

La política de generación de código asociada al modelo deberá aplicarse
de forma preventiva antes de enviar la petición al modelo, incorporando
las restricciones definidas por ABAPCompass a las instrucciones
proporcionadas al sistema de inteligencia artificial.

Estas instrucciones preventivas no constituirán una garantía absoluta
de cumplimiento debido a la naturaleza no determinista de los modelos
de lenguaje.

Las respuestas obtenidas mediante `AIProvider` se considerarán contenido
no confiable y deberán regresar a ABAPCompass para su tratamiento antes de
ser expuestas al consumidor de la API.

## 4.6 Política de respuesta

Además de las instrucciones preventivas incorporadas a las peticiones
enviadas al modelo, ABAPCompass aplicará controles deterministas sobre las
respuestas cuando la política asociada al modelo así lo requiera.

En v0.3.0, cuando la política de generación de código sea `none`, la API
aplicará una política de respuesta antes de construir la respuesta HTTP
pública.

La política comprobará la existencia de bloques de código delimitados
mediante triple acento grave. Cuando se detecte uno de estos bloques, su
contenido será eliminado y sustituido por un marcador interno que
permita conservar su posición dentro de la respuesta.

Si no se detectan bloques de código delimitados, el contenido se
mantendrá sin modificaciones.

La API incluirá además información estructurada que indicará si se ha
producido filtrado y, cuando corresponda, el motivo de dicho filtrado.

Este control se realizará después de obtener la respuesta generada por
el modelo y antes de devolverla al consumidor de la API.

La política no intentará identificar mediante heurísticas fragmentos de
código incluidos por el modelo dentro del texto ordinario de la
respuesta.

La interfaz web utilizará la información proporcionada por la API y los
marcadores presentes en el contenido para representar de forma
comprensible la posición de los bloques omitidos.

El texto utilizado por la interfaz para informar al usuario será
responsabilidad de la capa de presentación web y no formará parte del
contenido generado por el modelo.

## 4.7 Resolución dinámica de modelos

En v0.2.0, el proveedor y el modelo utilizados se determinan globalmente
durante el arranque de la aplicación.

En v0.3.0, cada petición dirigida a una capacidad de ABAPCompass
identificará explícitamente el modelo que deberá utilizarse.

La resolución seguirá el siguiente proceso:

1. La interfaz web obtiene los modelos soportados por ABAPCompass.
2. La interfaz presenta inicialmente el modelo predeterminado.
3. El usuario puede mantener el modelo seleccionado o seleccionar otro
   de los modelos disponibles.
4. La interfaz incluye el identificador público del modelo seleccionado
   en la petición.
5. El caso de uso obtiene de `ModelCatalog` la definición correspondiente
   al identificador recibido, produciéndose un error controlado si el
   modelo no está soportado.
6. El caso de uso proporciona la definición obtenida a
   `AIProviderResolver`.
7. `AIProviderResolver` obtiene el `AIProvider` adecuado a partir de
   dicha definición.
8. El caso de uso utiliza el `AIProvider` resuelto para ejecutar la
   operación.
9. La API aplica los controles posteriores sobre la respuesta cuando la
   política correspondiente así lo requiera.
10. La respuesta pública identifica el modelo utilizado y proporciona
    información sobre la política aplicada.

La selección realizada en la interfaz permanecerá activa mientras el
usuario utilice la aplicación y se aplicará a las distintas capacidades
hasta que se seleccione otro modelo. Esta selección constituye estado de
la interfaz y no estado de sesión mantenido por el backend.

Las peticiones a la API identificarán únicamente el modelo seleccionado
mediante su identificador público. No podrán proporcionar directamente
el identificador interno utilizado por el proveedor, la dirección del
servicio, credenciales ni otros parámetros de infraestructura.

De esta forma, ABAPCompass mantendrá el control sobre la resolución del
modelo y del proveedor. Los datos recibidos mediante la API no podrán
utilizarse para acceder a modelos o proveedores que no estén
contemplados por la aplicación.

El proveedor de inteligencia artificial y el modelo permanecerán fuera
de los casos de uso y de la interfaz web.

# 5. Catálogo y selección de modelos

El catálogo de modelos define qué modelos de inteligencia artificial
pueden utilizarse mediante ABAPCompass y establece la información necesaria
para identificarlos, presentarlos al usuario y resolver su ejecución.

ABAPCompass mantendrá una separación explícita entre la identidad pública
de un modelo dentro de la aplicación y los datos técnicos necesarios
para utilizarlo mediante un proveedor concreto.

La selección realizada por el usuario estará limitada a los modelos
incluidos en este catálogo.

## 5.1 Modelo de datos

Cada modelo soportado por ABAPCompass estará representado mediante una
definición de modelo.

La definición contendrá los siguientes atributos:

- `id`: identificador público y único del modelo dentro de ABAPCompass.
- `displayName`: nombre utilizado para presentar el modelo al usuario.
- `description`: descripción breve de la orientación o finalidad del
  modelo.
- `providerId`: identificador del proveedor encargado de ejecutar el
  modelo.
- `providerModel`: identificador técnico utilizado por el proveedor
  para acceder al modelo.
- `codeSuggestionMode`: política de generación de código asociada.

Conceptualmente, una definición tendrá la siguiente estructura:

```text
ModelDefinition
|
+-- id
+-- displayName
+-- description
+-- providerId
+-- providerModel
+-- codeSuggestionMode
```

El atributo `id` será el identificador público que deberán incluir las
peticiones dirigidas a las operaciones funcionales de la API.

Los atributos `providerId` y `providerModel` serán información interna
de ABAPCompass y no deberán ser proporcionados por la interfaz web al
ejecutar una operación.

Esta separación permite que la forma utilizada internamente para acceder
a un modelo pueda evolucionar sin modificar necesariamente el contrato
público de la API.

La Figura 3 representa conceptualmente la relación entre el
identificador público utilizado por ABAPCompass y la información interna
necesaria para resolver su ejecución.

```text
                Identificador público
                        |
                        v
              +-------------------+
              |   ModelCatalog    |
              +---------+---------+
                        |
                        v
              +-------------------+
              |  ModelDefinition  |
              +---------+---------+
                        |
             +----------+----------+
             |                     |
             v                     v
        providerId           providerModel
             |                     |
             +----------+----------+
                        |
                        v
              +-------------------+
              |    Proveedor IA   |
              +-------------------+
```

**Figura 3. Relación entre el identificador público del modelo y su
configuración interna.**

## 5.2 Catálogo inicial

ABAPCompass v0.3.0 dispondrá de tres modelos con orientaciones y políticas
de generación de código diferentes.

El catálogo será el siguiente:

| Orientación         | Identificador público   | Modelo                | Proveedor | Política   |
| ------------------- | ----------------------- | --------------------- | --------- | ---------- |
| Uso general         | `llama-3.2-3b`          | Llama 3.2 3B          | Ollama    | `none`     |
| Desarrollo asistido | `qwen-2.5-coder-7b`     | Qwen 2.5 Coder 7B     | Ollama    | `snippets` |
| Desarrollo avanzado | `deepseek-coder-v2-16b` | DeepSeek Coder V2 16B | Ollama    | `full`     |

La orientación indicada en la tabla describe el propósito previsto de
cada modelo dentro de ABAPCompass y facilita su presentación al usuario. No
constituye un atributo independiente de `ModelDefinition` ni determina
por sí misma la política aplicada.

La configuración interna correspondiente será:

| Identificador público   | `providerId` | `providerModel`         |
| ----------------------- | ------------ | ----------------------- |
| `llama-3.2-3b`          | `ollama`     | `llama3.2:3b`           |
| `qwen-2.5-coder-7b`     | `ollama`     | `qwen2.5-coder:7b`      |
| `deepseek-coder-v2-16b` | `ollama`     | `deepseek-coder-v2:16b` |

Los nombres técnicos utilizados por Ollama no formarán parte del
contrato que las operaciones funcionales exigirán a la interfaz web.

La incorporación de un modelo al catálogo significa que ABAPCompass conoce
su configuración y la política que debe aplicar durante su utilización.

No implica que ABAPCompass certifique la exactitud, calidad o adecuación de
las respuestas generadas por dicho modelo para un sistema SAP concreto.

## 5.3 Modelo predeterminado

ABAPCompass v0.3.0 utilizará como modelo predeterminado:

`qwen-2.5-coder-7b` — Qwen 2.5 Coder 7B.

La elección responde a que se trata de un modelo orientado a tareas de
programación y constituye una opción intermedia dentro del catálogo,
con una política `snippets` orientada a solicitar que la generación de
código se limite a fragmentos.

El modelo predeterminado será definido por ABAPCompass y comunicado a la
interfaz web junto con el catálogo de modelos disponibles.

La interfaz utilizará esta información para establecer la selección
inicial, evitando mantener una definición independiente del modelo
predeterminado.

Al iniciar la interfaz se seleccionará automáticamente el modelo
predeterminado.

Si el usuario selecciona posteriormente otro modelo, la nueva selección
se mantendrá mientras continúe utilizando la interfaz.

La selección inicial del modelo no implica que el backend mantenga una
sesión de usuario ni estado asociado a peticiones anteriores.

Cada operación continuará identificando explícitamente el modelo que
debe utilizar.

## 5.4 Políticas de generación de código

Cada definición de modelo contendrá una única política de generación de
código mediante el atributo `codeSuggestionMode`.

ABAPCompass v0.3.0 utilizará las siguientes políticas:

| Política   | Representación para el usuario | Comportamiento solicitado                                                                             |
| ---------- | ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `none`     | No genera código               | Se solicitará al modelo que la respuesta no proporcione código.                                       |
| `snippets` | Fragmentos de código           | Se permitirá al modelo proporcionar fragmentos de código limitados cuando resulten necesarios.        |
| `full`     | Soluciones completas           | Se permitirá al modelo proporcionar soluciones de código completas cuando las justifique la consulta. |

La política será determinada exclusivamente por el atributo
`codeSuggestionMode` de la definición existente en `ModelCatalog`.

En el catálogo de v0.3.0, la orientación de cada modelo será coherente
con su política de generación de código. No obstante, ABAPCompass no
deducirá la política a partir de dicha orientación, sino que utilizará
directamente el valor de `codeSuggestionMode` definido para el modelo.

El usuario no podrá modificar directamente la política ni seleccionar
una política distinta de la asignada al modelo.

Por tanto, no existirán combinaciones independientes como:

```text
Modelo: Qwen 2.5 Coder 7B
Política seleccionada por el usuario: full
```

La relación definida para v0.3.0 será:

```text
Llama 3.2 3B
        |
        +-- none

Qwen 2.5 Coder 7B
        |
        +-- snippets

DeepSeek Coder V2 16B
        |
        +-- full
```

La política se incorporará de forma preventiva a las instrucciones
enviadas al modelo antes de ejecutar la operación.

Debido a la naturaleza no determinista de los modelos de lenguaje, estas
instrucciones no constituyen por sí mismas una garantía absoluta de
cumplimiento.

Cuando la política sea `none`, ABAPCompass aplicará además un control
determinista sobre la respuesta para omitir los bloques de código
delimitados que hayan podido ser generados por el modelo.

Este control no intentará identificar como código fragmentos incluidos
dentro del texto ordinario de la respuesta.

Las políticas `snippets` y `full` determinarán el comportamiento
solicitado al modelo, pero no supondrán una garantía sobre la corrección,
seguridad, compilabilidad o adecuación del código generado.

La aplicación del aviso de validación profesional será independiente de
la política utilizada.

## 5.5 Selección y mantenimiento del modelo en la interfaz

La interfaz web dispondrá de un único modelo seleccionado en cada
momento.

La selección será común a las capacidades:

- Asistente SAP.
- Explicación de código ABAP.
- Revisión de código ABAP.

Al iniciar la interfaz se seleccionará automáticamente el modelo
predeterminado definido por ABAPCompass.

Si el usuario selecciona otro modelo, la nueva selección permanecerá
activa mientras continúe utilizando la interfaz y se aplicará a las
operaciones posteriores, independientemente de la capacidad desde la que
se ejecuten.

Por ejemplo:

```text
Inicio

  v

  |

  v
Llama 3.2 3B
  |
  +--> siguientes operaciones
```

La selección mantenida en la interfaz no será almacenada por el backend
como estado de sesión.

Cada petición incluirá el identificador público del modelo actualmente
seleccionado.

La persistencia de esta preferencia después de cerrar o reiniciar la
interfaz no forma parte del alcance de v0.3.0.

## 5.6 Validación y modelos no soportados

ABAPCompass aceptará únicamente identificadores públicos presentes en
`ModelCatalog`.

Cuando una petición incluya un identificador, ABAPCompass deberá comprobar
su existencia en el catálogo antes de intentar resolver el proveedor
correspondiente.

El comportamiento puede representarse conceptualmente de la siguiente
forma:

```text
ejecutar caso de uso con modelId
              |
              v
        ModelCatalog
              |
      +-------+-------+
      |               |
   existe          no existe
      |               |
      v               v
ModelDefinition   error controlado
      |
      v
AIProviderResolver
      |
      v
  AIProvider
      |
      v
ejecutar operación
```

No se utilizará el identificador recibido directamente como nombre de
modelo para realizar una petición a un proveedor de inteligencia
artificial.

Esta restricción evita que una petición pueda utilizar la API de
ABAPCompass como mecanismo para acceder a modelos arbitrarios que pudieran
existir en la infraestructura subyacente.

Una petición deberá rechazarse de forma controlada cuando:

- no incluya el identificador del modelo requerido.
- el identificador no exista en el catálogo.
- la definición correspondiente no pueda resolverse mediante un
  proveedor soportado.

La indisponibilidad temporal de un proveedor o de un modelo
correctamente configurado no convertirá el modelo en no soportado. Esta
situación se tratará como un error de ejecución o infraestructura y no
como un error de catálogo.

El catálogo representa, por tanto, los modelos admitidos funcionalmente
por ABAPCompass y no el estado operativo instantáneo de la infraestructura.

# 6. Diseño de la API REST

La API REST constituye el contrato público entre la interfaz web y el
backend de ABAPCompass.

La interfaz web deberá utilizar exclusivamente estos endpoints para
acceder a las capacidades de la aplicación y obtener la información
necesaria sobre los modelos soportados.

La API utilizará JSON como formato de intercambio de datos.

Los endpoints funcionales de asistencia requerirán que cada petición
identifique explícitamente el modelo que deberá utilizarse.

La API será responsable de validar los datos recibidos, coordinar la
ejecución de las operaciones y construir una respuesta pública que
incluya la información necesaria sobre el modelo utilizado, la política
aplicada y el aviso de validación profesional.

## 6.1 Consulta de modelos

### GET /models

Devuelve el catálogo público de modelos soportados por ABAPCompass y el
identificador del modelo predeterminado.

La respuesta utilizará el estado HTTP `200` y contendrá:

- `defaultModelId`: identificador público del modelo predeterminado.
- `models`: lista de modelos disponibles.

Cada elemento de `models` incluirá únicamente la información pública
necesaria para la interfaz:

- `id`.
- `displayName`.
- `description`.
- `codeSuggestionMode`.

La respuesta será:

```json
{
  "defaultModelId": "qwen-2.5-coder-7b",
  "models": [
    {
      "id": "llama-3.2-3b",
      "displayName": "Llama 3.2 3B",
      "description": "Modelo orientado a consultas de uso general.",
      "codeSuggestionMode": "none"
    },
    {
      "id": "qwen-2.5-coder-7b",
      "displayName": "Qwen 2.5 Coder 7B",
      "description": "Modelo orientado a tareas de desarrollo asistido.",
      "codeSuggestionMode": "snippets"
    },
    {
      "id": "deepseek-coder-v2-16b",
      "displayName": "DeepSeek Coder V2 16B",
      "description": "Modelo orientado a tareas de desarrollo avanzado.",
      "codeSuggestionMode": "full"
    }
  ]
}
```

La respuesta no expondrá información interna como:

- `providerId`.
- `providerModel`.
- direcciones de servicios.
- credenciales.
- parámetros internos de infraestructura.

La interfaz utilizará `defaultModelId` para establecer la selección
inicial.

## 6.2 Consulta SAP

### POST /assistant/query

Ejecuta una consulta relacionada con SAP utilizando el modelo
seleccionado.

Cuerpo de la petición:

```json
{
  "modelId": "qwen-2.5-coder-7b",
  "query": "¿Qué diferencia existe entre una BAPI y un RFC?",
  "context": "La consulta está relacionada con integración entre sistemas."
}
```

Campos:

- `modelId`: obligatorio. Identificador público de un modelo incluido en
  `ModelCatalog`.
- `query`: obligatorio. Texto de la consulta.
- `context`: opcional. Información adicional que puede ayudar a
  interpretar la consulta.

Los valores de tipo texto serán normalizados eliminando espacios
innecesarios al principio y al final.

Una cadena vacía o formada únicamente por espacios no será válida para
los campos obligatorios.

## 6.3 Explicación de código ABAP

### POST /assistant/explain

Solicita una explicación de código ABAP utilizando el modelo
seleccionado.

Cuerpo de la petición:

```json
{
  "modelId": "qwen-2.5-coder-7b",
  "code": "SELECT * FROM mara INTO TABLE lt_mara.",
  "context": "Código simplificado utilizado como ejemplo."
}
```

Campos:

- `modelId`: obligatorio.
- `code`: obligatorio. Código ABAP que se desea explicar.
- `context`: opcional.

ABAPCompass tratará el código recibido como datos de entrada. La operación
no implicará su compilación ni ejecución.

## 6.4 Revisión de código ABAP

### POST /assistant/review

Solicita una revisión de código ABAP utilizando el modelo seleccionado.

Cuerpo de la petición:

```json
{
  "modelId": "deepseek-coder-v2-16b",
  "code": "SELECT * FROM mara INTO TABLE lt_mara.",
  "context": "Revisar posibles problemas de rendimiento."
}
```

Campos:

- `modelId`: obligatorio.
- `code`: obligatorio. Código ABAP que se desea revisar.
- `context`: opcional.

ABAPCompass tratará el código recibido como datos de entrada y no lo
ejecutará ni modificará automáticamente.

## 6.5 Validación del modelo

Los endpoints:

- `POST /assistant/query`.
- `POST /assistant/explain`.
- `POST /assistant/review`.

requerirán siempre el campo `modelId`.

El valor deberá corresponder a un identificador público incluido en
`ModelCatalog`.

La validación y resolución seguirán conceptualmente el siguiente proceso:

```text
modelId
   |
   +-- ausente o vacío ----------> INVALID_REQUEST
   |
   v
ejecutar caso de uso
   |
   v
ModelCatalog
   |
   +-- no existe ----------------> MODEL_NOT_SUPPORTED
   |
   v
ModelDefinition
   |
   v
AIProviderResolver
   |
   v
AIProvider
   |
   v
ejecutar operación
```

El valor recibido en `modelId` se utilizará para obtener de
`ModelCatalog` la configuración del modelo correspondiente.

## 6.6 Respuesta satisfactoria

Las operaciones:

- `POST /assistant/query`.
- `POST /assistant/explain`.
- `POST /assistant/review`.

utilizarán una estructura común para las respuestas satisfactorias.

La respuesta HTTP utilizará el estado `200` y tendrá la siguiente
estructura:

```json
{
  "response": "Contenido generado para el usuario.",
  "modelId": "qwen-2.5-coder-7b",
  "codeSuggestionMode": "snippets",
  "policy": {
    "filtered": false
  },
  "validation": {
    "title": "Validación profesional requerida",
    "message": "Esta respuesta ha sido generada por IA y puede contener errores, omisiones o suposiciones incorrectas. Verifica la información antes de utilizarla. No ejecutes las acciones propuestas ni utilices el código generado directamente en entornos productivos sin una revisión técnica previa."
  }
}
```

Los campos tendrán el siguiente significado:

- `response`: contenido resultante de la operación que deberá presentar
  el cliente.
- `modelId`: identificador público del modelo utilizado.
- `codeSuggestionMode`: política de generación de código asociada al
  modelo.
- `policy`: información estructurada sobre la aplicación de la política
  de respuesta.
- `validation`: aviso de validación profesional proporcionado
  determinísticamente por ABAPCompass.

El contenido de `response` tendrá su origen en la salida generada por el
modelo, pero podrá haber sido transformado por la política de respuesta
antes de ser expuesto mediante la API.

El contenido generado por el modelo se considerará no confiable aunque
la operación haya finalizado satisfactoriamente.

El objeto `validation` no procederá del modelo de inteligencia
artificial. Será incorporado por ABAPCompass de forma determinista y
contendrá:

- `title`: título del aviso.
- `message`: mensaje de validación profesional.

El aviso definido para v0.3.0 será:

> **Validación profesional requerida**
>
> Esta respuesta ha sido generada por IA y puede contener errores,
> omisiones o suposiciones incorrectas. Verifica la información antes de
> utilizarla. No ejecutes las acciones propuestas ni utilices el código
> generado directamente en entornos productivos sin una revisión técnica
> previa.

ABAPCompass no ejecutará código ni acciones propuestas en el contenido
generado.

## 6.7 Información de política y contenido filtrado

El objeto `policy` permitirá al consumidor conocer si ABAPCompass ha
modificado la salida generada como consecuencia de la política de
respuesta.

Cuando no se haya producido filtrado:

```json
{
  "policy": {
    "filtered": false
  }
}
```

Cuando la política `none` provoque la eliminación de uno o más bloques
de código delimitados:

```json
{
  "policy": {
    "filtered": true,
    "reason": "CODE_SUGGESTION_NOT_ALLOWED"
  }
}
```

Los campos tendrán el siguiente significado:

- `filtered`: indica si la política de respuesta ha eliminado contenido
  de la salida generada.
- `reason`: identifica el motivo del filtrado cuando este se ha
  producido.

En v0.3.0, el valor definido para `reason` será
`CODE_SUGGESTION_NOT_ALLOWED`.

Cuando la política `none` detecte un bloque de código delimitado, la API
eliminará dicho bloque y conservará su posición mediante el marcador
interno:

`[[ABAPCOMPASS_CODE_BLOCK_FILTERED]]`

Por ejemplo, si el modelo genera una respuesta que contiene texto, un
bloque de código delimitado y posteriormente más texto, la API eliminará
el contenido del bloque y mantendrá en su posición el marcador interno.

El contenido de `response` podrá presentar conceptualmente el siguiente
aspecto:

```text
Puedes resolverlo de la siguiente forma:

[[ABAPCOMPASS_CODE_BLOCK_FILTERED]]

Después deberías validar el resultado.
```

El marcador permite que la interfaz web conserve la posición en la que
se encontraba el bloque eliminado y represente en ese lugar un aviso
comprensible para el usuario.

El marcador forma parte del mecanismo de intercambio entre la API y la
interfaz web. No procede del modelo de inteligencia artificial ni
constituye el texto que finalmente se muestra al usuario.

La interfaz web será responsable de transformar dicho marcador en la
representación visual correspondiente.

La política de respuesta no intentará identificar como código fragmentos
incluidos dentro del texto ordinario de la respuesta.

## 6.8 Errores

Los errores de la API utilizarán una estructura común formada por:

```json
{
  "code": "ERROR_CODE",
  "message": "Descripción comprensible del error."
}
```

Los códigos contemplados por la API serán:

| Estado HTTP | Código                    | Significado                                      |
| ----------- | ------------------------- | ------------------------------------------------ |
| `400`       | `INVALID_REQUEST`         | La petición no cumple el contrato requerido.     |
| `400`       | `MODEL_NOT_SUPPORTED`     | El modelo solicitado no está soportado.          |
| `503`       | `AI_PROVIDER_UNAVAILABLE` | El proveedor de IA no está disponible.           |
| `504`       | `AI_PROVIDER_TIMEOUT`     | El proveedor no respondió en el tiempo esperado. |
| `500`       | `INTERNAL_ERROR`          | Se produjo un error interno no clasificado.      |

Ejemplo de petición sin `modelId` válido:

```json
{
  "code": "INVALID_REQUEST",
  "message": "El campo modelId es obligatorio y debe contener un identificador de modelo."
}
```

Cuando el campo obligatorio de una consulta sea incorrecto, la API
responderá:

```json
{
  "code": "INVALID_REQUEST",
  "message": "El campo query es obligatorio y debe contener texto."
}
```

Cuando el campo obligatorio de una operación sobre código sea
incorrecto, la API responderá:

```json
{
  "code": "INVALID_REQUEST",
  "message": "El campo code es obligatorio y debe contener código ABAP."
}
```

Un modelo no soportado producirá:

```json
{
  "code": "MODEL_NOT_SUPPORTED",
  "message": "El modelo solicitado no está soportado por ABAPCompass."
}
```

La indisponibilidad del proveedor producirá:

```json
{
  "code": "AI_PROVIDER_UNAVAILABLE",
  "message": "El proveedor de IA no está disponible."
}
```

La expiración del tiempo de espera producirá:

```json
{
  "code": "AI_PROVIDER_TIMEOUT",
  "message": "El proveedor de IA no ha respondido dentro del tiempo esperado."
}
```

Un error interno no clasificado producirá:

```json
{
  "code": "INTERNAL_ERROR",
  "message": "Se ha producido un error interno."
}
```

Los mensajes públicos no deberán exponer trazas de excepción,
credenciales, rutas locales ni detalles internos innecesarios.

## 6.9 Endpoint de estado

### GET /health

ABAPCompass mantendrá un endpoint de estado destinado a comprobar que la
API se encuentra disponible.

La respuesta utilizará el estado HTTP `200` y proporcionará la
identificación del servicio, su versión y su estado.

La estructura será:

```json
{
  "service": "abapcompass-api",
  "version": "<versión de ABAPCompass>",
  "status": "ok"
}
```

El valor de `version` corresponderá a la versión identificada por
ABAPCompass.

Este endpoint no ejecutará operaciones de inteligencia artificial ni
requerirá la selección de un modelo.

Su finalidad será proporcionar una comprobación sencilla del estado de
la API para desarrollo, pruebas y diagnóstico básico.

## 6.10 Compatibilidad con v0.2.0

La versión v0.3.0 mantendrá las mismas capacidades funcionales
introducidas en v0.2.0:

- consulta SAP.
- explicación de código ABAP.
- revisión de código ABAP.

La evolución principal del contrato consistirá en exigir la selección
explícita del modelo en cada petición funcional y ampliar la respuesta
pública con información sobre el modelo utilizado, la política de
generación de código, el resultado de la política de respuesta y el
aviso de validación profesional.

La API REST continuará siendo el punto de entrada público a las
capacidades de ABAPCompass, independientemente de que estas se utilicen
desde la interfaz web u otro consumidor compatible con el contrato.

# 7. Diseño de la interfaz web

La interfaz web constituirá el principal medio de interacción del
usuario con ABAPCompass v0.3.0.

Su finalidad será proporcionar acceso a las capacidades existentes
mediante una experiencia de uso sencilla, manteniendo ocultos los
detalles técnicos relacionados con la API REST, los proveedores de
inteligencia artificial y la configuración interna de los modelos.

La interfaz será desarrollada con Vite, TypeScript, HTML y CSS nativos,
sin utilizar un framework de interfaz adicional, y se comunicará
exclusivamente con el backend mediante los contratos públicos definidos
en el capítulo 6.

## 7.1 Principios de diseño

El diseño de la interfaz seguirá los siguientes principios:

- proporcionar acceso claro a las tres capacidades principales de
  ABAPCompass.
- mantener una navegación coherente entre las distintas capacidades.
- utilizar un único modelo seleccionado para las operaciones realizadas
  desde la interfaz.
- mostrar información suficiente para que el usuario conozca el modelo
  seleccionado y su política de generación de código.
- diferenciar claramente los datos de entrada, las acciones disponibles
  y los resultados obtenidos.
- informar del estado de las operaciones mientras se encuentran en
  ejecución.
- presentar los errores mediante mensajes comprensibles.
- mostrar el aviso de validación profesional asociado a las respuestas
  satisfactorias.
- representar de forma explícita el contenido omitido por las políticas
  de respuesta.
- tratar como no confiable el contenido procedente tanto del usuario
  como de los modelos de inteligencia artificial.
- representar dicho contenido sin insertarlo como HTML interpretable.
- evitar exponer detalles internos relacionados con proveedores,
  configuraciones o infraestructura.
- permitir utilizar mediante teclado las operaciones principales.
- adaptarse razonablemente a diferentes tamaños de pantalla.

La interfaz priorizará la claridad funcional frente a la incorporación
de elementos visuales que no aporten información o capacidad de
interacción.

## 7.2 Estructura general

La interfaz estará organizada en torno a cuatro áreas funcionales:

- Inicio.
- Asistente SAP.
- Explicación ABAP.
- Revisión ABAP.

La página de inicio actuará como punto de entrada y permitirá identificar
las capacidades disponibles.

Las otras tres áreas proporcionarán los formularios y resultados
correspondientes a cada capacidad.

La navegación permitirá cambiar entre ellas manteniendo una estructura
común de interacción.

La selección del modelo permanecerá accesible desde las áreas
funcionales y será común a todas ellas.

La estructura conceptual será:

```text
ABAPCompass
|
+-- Inicio
|
+-- Asistente SAP
|
+-- Explicación ABAP
|
+-- Revisión ABAP
|
+-- Modelo seleccionado
```

La selección del modelo no constituirá una capacidad independiente ni
requerirá una página específica.

## 7.3 Página de inicio

La página de inicio presentará ABAPCompass y proporcionará acceso directo a
sus tres capacidades principales.

Cada capacidad podrá identificarse mediante un nombre y una breve
descripción de su finalidad.

Las capacidades presentadas serán:

- Asistente SAP, para realizar consultas relacionadas con SAP.
- Explicación ABAP, para obtener una explicación de código proporcionado
  por el usuario.
- Revisión ABAP, para solicitar observaciones y recomendaciones sobre
  código proporcionado por el usuario.

La página de inicio no ejecutará operaciones de inteligencia artificial
por sí misma.

Su función será facilitar el acceso a las capacidades y proporcionar una
primera referencia sobre el propósito de la aplicación.

## 7.4 Selector de modelo

La interfaz dispondrá de un selector que permita elegir uno de los
modelos soportados por ABAPCompass.

Los datos necesarios para construir el selector se obtendrán mediante:

```text
GET /models
```

La interfaz no mantendrá una lista independiente de los modelos
disponibles ni de sus configuraciones.

Una vez obtenida la respuesta, se seleccionará inicialmente el modelo
identificado mediante `defaultModelId`.

Para cada modelo, la interfaz permitirá conocer:

- su nombre.
- su descripción.
- su política de generación de código.

Las políticas técnicas se presentarán mediante textos comprensibles para
el usuario:

- `none`: No genera código.
- `snippets`: Fragmentos de código.
- `full`: Soluciones completas.

El selector no permitirá modificar independientemente la política
asociada al modelo.

Cuando el usuario seleccione otro modelo, la nueva selección permanecerá
activa mientras continúe utilizando la interfaz y se aplicará a las
operaciones posteriores de cualquiera de las tres capacidades.

El cambio de modelo no ejecutará por sí mismo ninguna operación contra
un proveedor de inteligencia artificial.

Si el catálogo no pudiera obtenerse, la interfaz informará del problema
y no permitirá ejecutar las capacidades hasta disponer de una selección
de modelo válida.

## 7.5 Asistente SAP

El área Asistente SAP permitirá formular consultas relacionadas con SAP.

El formulario contendrá:

- un campo obligatorio para la consulta.
- un campo opcional para proporcionar contexto adicional.
- acceso a la información del modelo actualmente seleccionado.
- una acción para enviar la consulta.

La operación requerirá una consulta válida y un modelo seleccionado.

Al ejecutarla, la interfaz realizará una petición a:

```text
POST /assistant/query
```

incluyendo el `modelId` correspondiente al modelo seleccionado.

Mientras la petición se encuentre en curso, la interfaz indicará
visualmente que la operación está siendo procesada y evitará envíos
duplicados de la misma operación.

Cuando la operación finalice correctamente, se representará la respuesta
recibida junto con la información asociada al modelo y el aviso de
validación profesional proporcionado por la API.

## 7.6 Explicación ABAP

El área Explicación ABAP permitirá introducir código ABAP y solicitar una
explicación de su funcionamiento.

El formulario contendrá:

- un área obligatoria para introducir el código ABAP.
- un campo opcional para proporcionar contexto adicional.
- acceso a la información del modelo actualmente seleccionado.
- una acción para solicitar la explicación.

La interfaz tratará el contenido introducido como datos de texto y no
intentará ejecutarlo ni validarlo mediante un sistema SAP.

Al ejecutar la operación se realizará una petición a:

```text
POST /assistant/explain
```

incluyendo el `modelId` seleccionado.

Durante el procesamiento se mostrará el estado correspondiente y se
evitarán envíos duplicados de la misma operación.

Una respuesta satisfactoria permitirá mostrar:

- la explicación generada.
- el modelo utilizado.
- la política de generación de código aplicada.
- el aviso de validación profesional.
- cualquier indicación de contenido omitido por la política de
  respuesta.

La interfaz preservará el formato del código introducido y representará
de forma legible los bloques de código que formen parte de la respuesta.

## 7.7 Revisión ABAP

El área Revisión ABAP permitirá introducir código ABAP y solicitar una
revisión orientada a detectar posibles problemas y oportunidades de
mejora.

El formulario contendrá:

- un área obligatoria para introducir el código ABAP.
- un campo opcional para proporcionar contexto adicional.
- acceso a la información del modelo actualmente seleccionado.
- una acción para solicitar la revisión.

Al ejecutar la operación se realizará una petición a:

```text
POST /assistant/review
```

incluyendo el `modelId` seleccionado.

La interfaz tratará el código recibido como datos y no presentará el
resultado como equivalente a una comprobación realizada mediante
compilación, ejecución o análisis estático sobre un sistema SAP.

Una respuesta satisfactoria permitirá mostrar:

- la revisión generada.
- el modelo utilizado.
- la política de generación de código aplicada.
- el aviso de validación profesional.
- cualquier indicación de contenido omitido por la política de
  respuesta.

Cuando la respuesta contenga código o propuestas de modificación, estas
se diferenciarán visualmente del contenido explicativo para facilitar su
lectura.

## 7.8 Presentación de resultados

Las tres capacidades utilizarán un criterio común para representar las
respuestas satisfactorias.

La interfaz distinguirá visualmente entre:

- el contenido resultante de la operación.
- la identificación del modelo utilizado.
- la política de generación de código aplicada.
- los avisos derivados de la política de respuesta.
- el aviso de validación profesional.

El contenido principal procederá del campo `response` recibido mediante
la API.

La identificación del modelo utilizado procederá de `modelId`.

La política de generación de código procederá de
`codeSuggestionMode`.

La información sobre el filtrado de contenido procederá del objeto
`policy`.

El aviso de validación profesional procederá del objeto `validation`.

La interfaz no generará por sí misma una copia del aviso de validación
profesional. Su responsabilidad será representar `validation.title` y
`validation.message` proporcionados por ABAPCompass mediante la API.

Cuando `policy.filtered` sea `true` y el contenido incluya el marcador
interno utilizado por ABAPCompass para identificar un bloque eliminado, la
interfaz sustituirá visualmente dicho marcador por un aviso situado en
la posición correspondiente.

En v0.3.0, el aviso utilizado para esta situación será:

```text
Código omitido por política

El modelo seleccionado no permite sugerencias de código.
ABAPCompass ha omitido este bloque de la respuesta.
```

Este texto será responsabilidad de la interfaz web y no formará parte
del contenido generado por el modelo ni del aviso de validación
profesional proporcionado por la API.

Cuando el resultado contenga texto y bloques de código permitidos, la
representación distinguirá ambos tipos de contenido y preservará el
formato de los bloques de código.

El contenido procedente de la respuesta del modelo se tratará como
contenido no confiable. Su representación se realizará mediante
elementos de texto o elementos específicos para código, sin insertar la
respuesta como HTML interpretable.

El mismo principio se aplicará al contenido introducido por el usuario
cuando deba ser representado nuevamente en la interfaz.

La interfaz no interpretará una respuesta satisfactoria como garantía de
corrección técnica del contenido generado.

## 7.9 Estados de la interfaz

Cada operación funcional gestionará explícitamente su estado.

Como mínimo se contemplarán conceptualmente los siguientes estados:

```text
idle
  |
  | ejecutar
  v
loading
  |
  +-- éxito --> success
  |
  +-- error --> error
```

El estado `idle` representará una operación preparada para recibir o
modificar datos de entrada.

El estado `loading` representará una petición enviada y todavía no
resuelta.

El estado `success` representará una petición completada correctamente y
permitirá mostrar el resultado recibido.

El estado `error` representará una petición que no ha podido completarse
correctamente.

La interfaz evitará que el resultado de una operación anterior pueda
confundirse con el estado de una nueva operación en curso.

Una nueva ejecución actualizará de forma coherente el estado y la
información presentada.

## 7.10 Tratamiento de errores

Los errores recibidos desde la API se transformarán en información
comprensible para el usuario.

La interfaz podrá utilizar el código estable incluido en el contrato de
error para adaptar el mensaje presentado.

Como mínimo se contemplarán situaciones relacionadas con:

- datos obligatorios no proporcionados.
- modelo no soportado.
- proveedor o modelo no disponible.
- tiempo de espera agotado.
- error interno inesperado.
- imposibilidad de comunicación con la API.

La interfaz no mostrará directamente trazas de excepción, respuestas
internas del proveedor ni detalles técnicos que no resulten útiles para
el usuario.

Cuando un error permita volver a ejecutar la operación, la interfaz
mantendrá los datos introducidos para evitar que el usuario tenga que
proporcionarlos nuevamente.

Los errores no mostrarán el aviso de validación profesional, ya que este
se asociará exclusivamente a respuestas satisfactorias.

## 7.11 Estado del modelo seleccionado

La selección del modelo será común a las distintas áreas funcionales de
la interfaz web y se mantendrá mientras el usuario continúe utilizando
la aplicación.

Este estado estará disponible para las tres capacidades y se actualizará
cuando el usuario seleccione otro modelo.

Conceptualmente:

```text
Modelo seleccionado
        |
        +--> Asistente SAP
        |
        +--> Explicación ABAP
        |
        +--> Revisión ABAP
```

Las áreas funcionales utilizarán este estado para incorporar `modelId` a
cada petición, pero no serán responsables de determinar el proveedor ni
la política correspondiente.

La selección permanecerá activa durante la utilización de la interfaz.

No será necesario persistirla en almacenamiento local, cookies ni
backend una vez finalizada la utilización de la interfaz.

Si la interfaz se inicia nuevamente, volverá a obtener el catálogo y
seleccionará el modelo indicado mediante `defaultModelId`.

## 7.12 Diseño adaptable y accesibilidad

La interfaz se diseñará principalmente para su utilización desde equipos
de escritorio, manteniendo un comportamiento razonable en pantallas de
menor tamaño.

La adaptación no eliminará ninguna de las capacidades principales.

Los controles interactivos dispondrán de textos o etiquetas que permitan
identificar su finalidad.

Los campos de formulario estarán asociados con sus etiquetas y
permitirán la navegación mediante teclado.

Los estados de error no se comunicarán exclusivamente mediante elementos
visuales como el color.

Las acciones principales podrán ejecutarse mediante teclado, sin
requerir necesariamente el uso del ratón.

El código ABAP y los fragmentos de código presentes en las respuestas se
mostrarán mediante una representación adecuada para contenido
preformateado.

La implementación priorizará elementos HTML semánticos y evitará
soluciones que dificulten innecesariamente la accesibilidad.

## 7.13 Límites de responsabilidad de la interfaz

La interfaz web será responsable de:

- presentar las capacidades disponibles.
- obtener los datos introducidos por el usuario.
- obtener y presentar el catálogo público de modelos.
- mantener el modelo seleccionado durante su utilización.
- construir las peticiones conforme al contrato público de la API.
- representar los estados de ejecución.
- presentar las respuestas y errores recibidos.
- diferenciar visualmente texto, bloques de código y contenido omitido
  por las políticas de respuesta.
- representar el aviso de validación profesional recibido mediante la
  API.
- representar el contenido no confiable sin insertarlo como HTML
  interpretable.

La interfaz web no será responsable de:

- determinar qué proveedor corresponde al modelo seleccionado.
- conocer el identificador técnico utilizado por el proveedor.
- modificar la política de generación asociada a un modelo.
- construir las instrucciones internas enviadas al modelo.
- generar el contenido del aviso de validación profesional.
- decidir qué contenido debe ser filtrado por la política de respuesta.
- acceder directamente a proveedores de inteligencia artificial.
- validar, compilar o ejecutar código ABAP.
- ejecutar código o acciones propuestas en las respuestas generadas.
- determinar si una respuesta generada es técnicamente correcta.

Estas responsabilidades permanecerán en los componentes correspondientes
del backend o, en el caso de la validación final de las respuestas, en el
profesional que utilice ABAPCompass.

# 8. Estructura técnica del proyecto

ABAPCompass v0.3.0 mantendrá una organización modular basada en aplicaciones
y paquetes con responsabilidades diferenciadas.

La estructura física del repositorio reflejará la separación entre la
interfaz web, la API REST, la lógica reutilizable del núcleo y las
implementaciones concretas necesarias para acceder a los proveedores de
inteligencia artificial.

La organización deberá facilitar la identificación de responsabilidades,
evitar dependencias innecesarias y mantener el desacoplamiento definido
por la arquitectura.

## 8.1 Organización general

ABAPCompass estará organizado principalmente mediante las siguientes
unidades:

```text
ABAPCompass
|
+-- apps
|   |
|   +-- api
|   |
|   +-- web
|
+-- packages
|   |
|   +-- core
|
+-- docs
|
+-- scripts
```

La aplicación `api` expondrá mediante HTTP las capacidades de ABAPCompass y
contendrá la composición de dependencias, las implementaciones concretas
de infraestructura y los componentes de presentación asociados a la API.

La aplicación `web` contendrá la interfaz de usuario desarrollada con
Vite, TypeScript, HTML y CSS nativos y consumirá exclusivamente los
contratos públicos proporcionados por `api`.

El paquete `core` contendrá los conceptos de dominio, los casos de uso,
los contratos definidos mediante puertos y los componentes de aplicación
independientes de las tecnologías concretas de presentación e
infraestructura.

La documentación, los scripts y las configuraciones transversales se
mantendrán fuera de estas unidades cuando no pertenezcan específicamente
a ninguna de ellas.

## 8.2 Paquete core

El paquete `packages/core` concentrará la lógica reutilizable e
independiente de los mecanismos concretos de presentación e
infraestructura.

Su estructura principal será:

```text
packages/core/src
|
+-- index.ts
|
+-- application
|   |
|   +-- models
|   |   |
|   |   +-- model-catalog.ts
|   |   +-- model-definition.ts
|   |
|   +-- ports
|   |   |
|   |   +-- ai-provider.ts
|   |
|   +-- providers
|   |   |
|   |   +-- ai-provider-resolver.ts
|   |
|   +-- use-cases
|       |
|       +-- answer-query.ts
|       +-- explain-abap-code.ts
|       +-- review-abap-code.ts
|
+-- domain
    |
    +-- abap-code.ts
    +-- context.ts
    +-- query.ts
    +-- response.ts
    +-- sap-professional.ts
```

El dominio representará los conceptos propios de ABAPCompass sin depender
de Express, Vite, Ollama ni de otras tecnologías de infraestructura o
presentación.

La capa de aplicación contendrá:

- las definiciones y el catálogo de modelos.
- el puerto `AIProvider`.
- el mecanismo `AIProviderResolver`.
- los casos de uso disponibles.

Los casos de uso dependerán del puerto `AIProvider` y de los mecanismos
de aplicación necesarios para resolver el modelo seleccionado, evitando
dependencias directas respecto a implementaciones concretas como Ollama.

## 8.3 ModelCatalog

`ModelCatalog` se ubicará en:

```text
packages/core/src/application/models
```

Su responsabilidad será mantener las definiciones de los modelos
soportados por ABAPCompass y proporcionar las operaciones necesarias para
consultarlas.

La definición de cada modelo incluirá la información necesaria para:

- identificarlo públicamente.
- presentarlo al usuario.
- determinar el proveedor correspondiente.
- identificar el modelo técnico utilizado por dicho proveedor.
- conocer la política `codeSuggestionMode` asociada.

`ModelCatalog` no dependerá de HTTP, de la interfaz web ni de una
implementación concreta de proveedor.

La API utilizará la información del catálogo para construir la
representación pública de `GET /models`, excluyendo las propiedades
internas que no deban formar parte del contrato HTTP.

## 8.4 AIProviderResolver

`AIProviderResolver` se ubicará en:

```text
packages/core/src/application/providers
```

Su responsabilidad será resolver la implementación de `AIProvider`
correspondiente al modelo seleccionado.

La resolución utilizará la definición previamente obtenida desde
`ModelCatalog`.

Los casos de uso no deberán incorporar condiciones específicas
relacionadas con implementaciones concretas de infraestructura.

Conceptualmente, se evitarán dependencias como:

```text
si modelo = X -> utilizar Ollama
si modelo = Y -> utilizar otro proveedor
```

La decisión sobre qué implementación de `AIProvider` utilizar deberá
permanecer encapsulada en el mecanismo de resolución.

## 8.5 Aplicación api

La aplicación `apps/api` será responsable de exponer mediante HTTP las
capacidades proporcionadas por ABAPCompass y de integrar los componentes
necesarios para ejecutarlas.

Su estructura principal será:

```text
apps/api/src
|
+-- app.ts
+-- index.ts
+-- server-config.ts
+-- server.ts
|
+-- application
|   |
|   +-- assistant-application.ts
|
+-- infrastructure
|   |
|   +-- ai
|       |
|       +-- ai-provider-error.ts
|       +-- ai-provider-factory.ts
|       +-- llm-prompt-policy.ts
|       +-- ollama-ai-provider.ts
|       +-- ollama-config.ts
|       +-- static-ai-provider.ts
|
+-- presentation
    |
    +-- error-handler.ts
    |
    +-- assistant
    |   |
    |   +-- assistant-response-policy.ts
    |   +-- controller.ts
    |   +-- professional-validation.ts
    |   +-- routes.ts
    |
    +-- health
    |   |
    |   +-- routes.ts
    |
    +-- models
        |
        +-- routes.ts
```

La organización separará tres responsabilidades principales:

- composición y coordinación de la aplicación.
- infraestructura necesaria para acceder a proveedores de IA.
- presentación mediante HTTP.

La API dependerá de `packages/core` para utilizar los casos de uso,
modelos, puertos y mecanismos de resolución definidos por el núcleo.

## 8.6 Composición de la aplicación

La composición necesaria para proporcionar las capacidades del asistente
se localizará en la capa de aplicación de `apps/api`.

`assistant-application.ts` será responsable de integrar los componentes
necesarios para ejecutar las operaciones de ABAPCompass.

Esta composición permitirá conectar:

- `ModelCatalog`.
- `AIProviderResolver`.
- las implementaciones disponibles de `AIProvider`.
- los casos de uso de consulta, explicación y revisión.

La composición de dependencias permanecerá fuera de los casos de uso,
evitando que estos sean responsables de crear implementaciones concretas
de infraestructura.

## 8.7 Infraestructura de inteligencia artificial

Las implementaciones concretas necesarias para comunicarse con
proveedores de inteligencia artificial se ubicarán en:

```text
apps/api/src/infrastructure/ai
```

En v0.3.0 se dispondrá de:

- `OllamaAIProvider`, para realizar peticiones reales mediante Ollama.
- `StaticAIProvider`, para proporcionar respuestas controladas en pruebas
  y escenarios de desarrollo.
- una fábrica de proveedores encargada de proporcionar las
  implementaciones disponibles.
- configuración específica de Ollama.
- tipos de error asociados a la comunicación con proveedores.

`OllamaAIProvider` implementará el contrato definido por `AIProvider`
sin trasladar detalles específicos de Ollama a los casos de uso.

`StaticAIProvider` proporcionará un comportamiento determinista que
permita ejecutar pruebas sin requerir un modelo de inteligencia
artificial real.

`StaticAIProvider` no formará parte del catálogo público de modelos ni
será seleccionable desde la interfaz web.

## 8.8 Política preventiva de generación

La construcción de las instrucciones preventivas relacionadas con las
políticas de generación de código se mantendrá separada de los casos de
uso y de la presentación HTTP.

La lógica correspondiente se ubicará en:

```text
apps/api/src/infrastructure/ai/llm-prompt-policy.ts
```

Esta responsabilidad permitirá incorporar a las instrucciones enviadas
al modelo el comportamiento esperado para las políticas `none`,
`snippets` y `full`.

La política preventiva tendrá como objetivo orientar el comportamiento
del modelo, pero no constituirá una garantía determinista de
cumplimiento.

## 8.9 Política de respuesta

El control determinista aplicado sobre las respuestas se ubicará en la
capa de presentación de la API:

```text
apps/api/src/presentation/assistant/assistant-response-policy.ts
```

Esta política será aplicada antes de construir la respuesta HTTP
satisfactoria.

Cuando `codeSuggestionMode` sea `none`, comprobará la existencia de
bloques de código delimitados.

Cuando se detecten, dichos bloques serán eliminados y sustituidos por un
marcador interno que permita conservar su posición dentro del contenido.

La política proporcionará además metadatos estructurados indicando si se
ha producido filtrado y, cuando corresponda, el motivo.

Esta responsabilidad permanecerá separada de:

- `AIProvider`.
- el modelo de inteligencia artificial.
- la interfaz web.
- el aviso de validación profesional.

## 8.10 Presentación de la API

La capa de presentación se ubicará en:

```text
apps/api/src/presentation
```

El área `assistant` contendrá:

- las rutas de las tres operaciones funcionales.
- el controlador encargado de validar y transformar las peticiones.
- la aplicación de la política de respuesta.
- la incorporación determinista del aviso de validación profesional.

El área `models` proporcionará el endpoint público del catálogo de
modelos.

El área `health` proporcionará el endpoint de estado de la API.

El tratamiento común de errores se mantendrá separado de los
controladores funcionales y transformará los errores internos en el
contrato HTTP público definido por ABAPCompass.

## 8.11 Aplicación web

La aplicación `apps/web` contendrá la interfaz de usuario de ABAPCompass.

Su estructura en v0.3.0 será deliberadamente sencilla:

```text
apps/web/src
|
+-- assistant-ui.ts
+-- main.ts
+-- styles.css
+-- vite-env.d.ts
```

La interfaz utilizará Vite como herramienta de desarrollo y construcción
y TypeScript para implementar su comportamiento.

No se utilizará React ni otro framework de interfaz adicional.

`main.ts` coordinará la interacción principal con el usuario, el acceso a
la API, la selección del modelo y la representación de los resultados.

`assistant-ui.ts` contendrá la lógica auxiliar necesaria para interpretar
y segmentar el contenido recibido en las respuestas del asistente,
incluyendo el tratamiento de bloques de código y de los marcadores
correspondientes a contenido filtrado.

`styles.css` contendrá la presentación visual de la interfaz.

La simplicidad de esta estructura responde al alcance limitado de
v0.3.0 y evita introducir capas o dependencias que no proporcionen una
responsabilidad necesaria.

## 8.12 Acceso a la API desde la interfaz web

La interfaz web utilizará exclusivamente los contratos HTTP públicos
expuestos por `apps/api`.

Como mínimo consumirá:

```text
GET  /models
POST /assistant/query
POST /assistant/explain
POST /assistant/review
```

La interfaz no accederá directamente a:

- `packages/core`.
- `OllamaAIProvider`.
- `ModelCatalog`.
- `AIProviderResolver`.
- configuraciones internas de modelos o proveedores.

Durante el desarrollo local, Vite podrá utilizar una configuración de
proxy para dirigir las peticiones correspondientes hacia la API sin
alterar el contrato utilizado por la interfaz.

La aplicación web no contendrá direcciones directas de Ollama,
credenciales ni información necesaria para acceder a proveedores de
inteligencia artificial.

## 8.13 Estado de la interfaz

La selección del modelo se mantendrá como estado de la propia interfaz.

La solución deberá permitir:

- establecer inicialmente el modelo indicado mediante
  `defaultModelId`.
- consultar el modelo seleccionado desde las tres operaciones.
- modificar la selección mediante el selector de modelos.
- conservar la selección mientras la interfaz permanezca activa.

La selección no será almacenada por el backend como estado de sesión.

Tampoco será necesario persistirla mediante `localStorage`, cookies u
otros mecanismos de almacenamiento permanente.

Las operaciones posteriores incluirán explícitamente el `modelId`
correspondiente a la selección activa.

## 8.14 Representación segura de contenido

La interfaz web tratará como no confiable tanto el contenido introducido
por el usuario como el contenido recibido desde las respuestas del
asistente.

La representación del contenido se realizará mediante elementos DOM
creados de forma explícita y asignación de contenido textual, evitando
insertar directamente como HTML interpretable las respuestas generadas
por los modelos.

Los bloques de código permitidos se representarán mediante elementos
adecuados para contenido preformateado.

Cuando la API indique que un bloque ha sido filtrado y mantenga su
posición mediante el marcador definido para este propósito, la interfaz
lo sustituirá por el aviso visual correspondiente.

La interfaz no ejecutará código ni acciones incluidas en las respuestas
generadas.

## 8.15 Configuración

La configuración dependiente del entorno deberá permanecer separada del
código cuando pueda variar entre instalaciones.

Podrán requerir configuración valores como:

- dirección y puerto de la API.
- dirección del servicio de Ollama.
- tiempos de espera.

Los valores sensibles permanecerán exclusivamente en el backend.

Los archivos que contengan secretos no deberán incorporarse al
repositorio.

Los archivos de ejemplo utilizados para documentar configuración podrán
incluir únicamente valores no sensibles.

## 8.16 Dependencias entre componentes

Las dependencias principales mantendrán conceptualmente la siguiente
dirección:

```text
apps/web
   |
   | HTTP / JSON
   v
apps/api
   |
   v
packages/core
```

La aplicación `web` no dependerá directamente del código interno de
`core`.

La aplicación `api` utilizará los contratos y funcionalidades definidos
por `core` y proporcionará las implementaciones concretas necesarias
para ejecutarlos.

`packages/core` no dependerá de `apps/api` ni de `apps/web`.

Las implementaciones concretas de `AIProvider` dependerán del puerto
definido por el núcleo, sin introducir dependencias de infraestructura
en los casos de uso.

Esta dirección de dependencias se mantendrá también en las pruebas,
evitando accesos directos que no representen la forma normal de
colaboración entre los componentes.

## 8.17 Criterios para la estructura física

La implementación favorecerá una estructura suficientemente explícita
para identificar la responsabilidad de cada componente sin introducir
fragmentación innecesaria.

Se evitarán:

- archivos que acumulen responsabilidades no relacionadas.
- duplicación de contratos o tipos equivalentes sin una necesidad
  justificada.
- dependencias circulares.
- acceso directo desde la interfaz web a componentes internos del
  backend.
- referencias directas a proveedores concretos desde los casos de uso.
- incorporación de abstracciones que no respondan a una necesidad real
  de la versión.

La estructura podrá evolucionar cuando una necesidad técnica justificada
lo requiera, siempre que se mantengan las responsabilidades y reglas de
dependencia definidas por la arquitectura.

# 9. Seguridad y uso responsable

ABAPCompass v0.3.0 deberá mantener medidas de seguridad adecuadas a su
alcance y a su naturaleza como aplicación que procesa información
proporcionada por el usuario mediante modelos de inteligencia
artificial.

La incorporación de una interfaz web y de la selección dinámica de
modelos amplía los puntos de entrada de la aplicación y requiere
establecer controles específicos para evitar que datos recibidos desde
el cliente puedan utilizarse para modificar decisiones internas de
configuración o acceder a recursos no autorizados.

Tanto los datos proporcionados por el usuario como las respuestas
generadas por los modelos de inteligencia artificial se considerarán
contenido no confiable.

Las respuestas generadas no deberán interpretarse como una garantía de
corrección técnica y ABAPCompass no ejecutará código ni acciones propuestas
en ellas.

## 9.1 Validación de entradas

Toda información recibida mediante la API REST deberá considerarse
entrada no confiable y validarse antes de ejecutar los casos de uso.

La validación deberá comprobar, según la operación:

- presencia de los campos obligatorios.
- tipo y estructura de los datos recibidos.
- validez del identificador del modelo.
- cumplimiento de los límites establecidos para los campos de entrada.

La validación realizada en la interfaz web tendrá como finalidad mejorar
la experiencia de usuario, pero no sustituirá la validación realizada
por el backend.

Por tanto, una petición realizada directamente contra la API estará
sometida a los mismos controles que una petición originada desde la
interfaz web.

Los datos introducidos por el usuario no deberán utilizarse para
modificar configuraciones internas de la aplicación.

## 9.2 Control de selección de modelos

La selección dinámica de modelos se realizará exclusivamente mediante
identificadores públicos incluidos en `ModelCatalog`.

El valor de `modelId` recibido mediante una petición deberá validarse
contra el catálogo antes de resolver el proveedor correspondiente.

El identificador recibido no deberá utilizarse directamente como nombre
técnico de un modelo de un proveedor.

La petición tampoco podrá especificar directamente:

- el proveedor que deberá utilizarse.
- el identificador técnico del modelo en el proveedor.
- la dirección del servicio del proveedor.
- credenciales.
- parámetros internos de configuración.
- la política de generación de código.

Estos valores serán determinados exclusivamente por ABAPCompass a partir de
la configuración asociada al modelo seleccionado.

De esta forma, el contrato público no podrá utilizarse para acceder
arbitrariamente a modelos o proveedores no contemplados por la
aplicación.

## 9.3 Protección de credenciales y configuración

La interfaz web no contendrá credenciales ni secretos necesarios para
acceder a servicios externos.

Si una futura implementación de `AIProvider` requiriera credenciales,
estas deberán permanecer exclusivamente en el backend.

Los valores sensibles no deberán:

- incorporarse directamente al código fuente.
- incluirse en archivos versionados.
- enviarse a la interfaz web.
- incluirse en respuestas de la API.
- registrarse en logs.

La configuración que pueda variar entre entornos deberá obtenerse
mediante mecanismos externos al código fuente.

Cuando se proporcionen archivos de configuración de ejemplo, estos
deberán contener únicamente nombres de variables y valores no sensibles
adecuados para documentar la configuración necesaria.

## 9.4 Tratamiento del contenido introducido por el usuario

Las consultas, el contexto y el código ABAP proporcionados por el
usuario se utilizarán exclusivamente como datos de entrada para las
operaciones correspondientes.

ABAPCompass no ejecutará automáticamente código proporcionado por el
usuario.

La operación de explicación no implicará que el código haya sido
compilado ni validado mediante un sistema SAP.

La operación de revisión tampoco implicará análisis estático,
compilación o ejecución real del código.

La interfaz deberá representar el código y demás contenido proporcionado
por el usuario como datos, sin interpretarlos como HTML ejecutable ni
como elementos activos de la propia aplicación.

El contenido procedente del usuario deberá tratarse de forma segura
durante su representación para evitar que pueda interpretarse como
contenido activo de la interfaz.

## 9.5 Instrucciones proporcionadas a los modelos

Los datos introducidos por el usuario formarán parte de la información
proporcionada al modelo para ejecutar la operación solicitada.

ABAPCompass deberá mantener separadas conceptualmente las instrucciones
definidas por la aplicación y el contenido proporcionado por el usuario.

Las instrucciones internas establecerán el comportamiento esperado para
cada capacidad y, cuando corresponda, la política de generación de
código asociada al modelo.

El contenido introducido por el usuario no deberá utilizarse para
modificar la configuración interna de ABAPCompass ni determinar
directamente el proveedor o la política de generación aplicada.

Las políticas `none`, `snippets` y `full` se incorporarán a las
instrucciones proporcionadas al modelo según la definición existente en
`ModelCatalog`.

Estas instrucciones constituyen un control preventivo destinado a
orientar el comportamiento del modelo, pero no garantizan que la
respuesta generada respete las instrucciones recibidas.

Por este motivo, los controles que requieran un cumplimiento
determinista deberán aplicarse por la propia aplicación y no depender
exclusivamente del comportamiento del modelo.

## 9.6 Tratamiento de respuestas generadas

Las respuestas producidas por los modelos de inteligencia artificial
deberán considerarse contenido generado y no confiable.

ABAPCompass no deberá asumir que una respuesta:

- es técnicamente correcta.
- contiene código ABAP sintácticamente válido.
- puede compilarse correctamente.
- respeta las particularidades de un sistema SAP determinado.
- cumple todos los requisitos de seguridad o rendimiento aplicables.
- puede utilizarse directamente en un entorno productivo.

ABAPCompass no ejecutará automáticamente código ni acciones propuestas en
una respuesta generada.

Cuando una respuesta incluya código permitido por la política asociada
al modelo, este se presentará únicamente como contenido para su revisión
por parte del usuario.

La política `codeSuggestionMode` tendrá dos niveles diferenciados de
aplicación:

1. Las instrucciones proporcionadas al modelo actuarán como control
   preventivo para orientar la generación.
2. Cuando `codeSuggestionMode` sea `none`, ABAPCompass aplicará además un
   control determinista sobre la respuesta antes de exponerla mediante
   la API.

El control determinista identificará únicamente bloques de código
delimitados estructuralmente.

Cuando se detecte uno de estos bloques bajo la política `none`, ABAPCompass
eliminará únicamente el bloque afectado, conservará el resto de la
respuesta e incorporará en su posición el marcador interno definido para
representar contenido filtrado.

La API indicará además mediante `policy.filtered` que se ha producido
filtrado y proporcionará mediante `policy.reason` el motivo cuando
corresponda.

Este control no intentará identificar como código fragmentos incluidos
dentro del texto ordinario de la respuesta.

La existencia de estos controles no convertirá el contenido restante en
información técnicamente validada.

## 9.7 Aviso de validación profesional

Toda respuesta satisfactoria obtenida mediante una capacidad funcional
incorporará el aviso de validación profesional definido por ABAPCompass.

El aviso será generado por la aplicación de forma determinista e
independiente de la respuesta producida por el modelo.

El modelo de inteligencia artificial no será responsable de generar,
modificar ni decidir la inclusión del aviso.

El aviso definido para v0.3.0 será:

> **Validación profesional requerida**
>
> Esta respuesta ha sido generada por IA y puede contener errores,
> omisiones o suposiciones incorrectas. Verifica la información antes de
> utilizarla. No ejecutes las acciones propuestas ni utilices el código
> generado directamente en entornos productivos sin una revisión técnica
> previa.

La API incorporará el aviso a las respuestas satisfactorias mediante una
estructura independiente del contenido generado:

```text
validation
|
+-- title
|
+-- message
```

La interfaz web será responsable de representar de forma visible el
título y el mensaje recibidos.

La presencia del aviso no sustituirá ninguna medida técnica de seguridad
ni convertirá una respuesta generada en una solución validada.

## 9.8 Tratamiento seguro de errores

Los errores internos deberán transformarse antes de formar parte de una
respuesta pública.

Las respuestas de error no deberán incluir:

- trazas completas de excepciones.
- rutas locales del sistema.
- credenciales.
- variables de entorno sensibles.
- configuración interna de proveedores.
- respuestas internas completas de proveedores cuando contengan
  información innecesaria para el usuario.

La API proporcionará códigos de error estables y mensajes adecuados para
el consumidor del contrato.

La información técnica necesaria para diagnosticar un problema podrá
registrarse en el backend cuando resulte apropiado, respetando las
reglas establecidas para los logs.

## 9.9 Registro de información

Los registros de la aplicación deberán contener únicamente la
información necesaria para facilitar el diagnóstico y seguimiento
técnico.

No deberán registrarse credenciales ni secretos.

Cuando resulte necesario registrar información relacionada con una
operación, se evitará almacenar innecesariamente el contenido completo
de consultas, contextos, código ABAP o respuestas generadas.

Los registros deberán permitir identificar técnicamente errores
relevantes sin convertirse en un mecanismo de almacenamiento de las
conversaciones del usuario.

La persistencia de conversaciones no forma parte del alcance de v0.3.0.

## 9.10 Seguridad de la interfaz web

La interfaz web deberá utilizar exclusivamente la API REST de ABAPCompass
para acceder a las capacidades del backend.

No accederá directamente a proveedores de inteligencia artificial ni
incorporará información interna necesaria para utilizarlos.

Los datos procedentes tanto del usuario como de las respuestas de la API
se considerarán contenido no confiable durante su representación.

La interfaz utilizará elementos DOM creados de forma explícita y
asignará el contenido textual mediante mecanismos que no provoquen su
interpretación como HTML ejecutable.

Los bloques de código se representarán mediante elementos destinados a
contenido preformateado y tampoco se insertarán como HTML interpretable.

Cuando la API haya eliminado un bloque de código por aplicación de la
política de respuesta, la interfaz utilizará la información recibida para
representar visualmente el aviso correspondiente en la posición del
contenido omitido.

La decisión de filtrar contenido corresponderá al backend. La interfaz
será responsable únicamente de representar de forma adecuada el
resultado de esa decisión.

Las validaciones realizadas en el frontend no se considerarán controles
de seguridad suficientes por sí mismas.

Toda decisión relevante para la seguridad, como la aceptación del modelo
solicitado o la aplicación de la política de respuesta, deberá realizarse
o comprobarse en el backend.

## 9.11 Dependencias de terceros

Las nuevas dependencias incorporadas para implementar la interfaz web o
las funcionalidades de v0.3.0 deberán limitarse a aquellas que
proporcionen una utilidad justificada.

Antes de incorporar una dependencia deberá valorarse si la funcionalidad
puede resolverse razonablemente mediante las capacidades ya disponibles
en el proyecto o en las tecnologías utilizadas.

Las dependencias deberán declararse explícitamente mediante los
mecanismos de gestión de paquetes del proyecto y quedar sujetas a las
validaciones automatizadas definidas para el repositorio.

No deberán incorporarse dependencias únicamente para resolver
funcionalidades menores cuando ello aumente innecesariamente la
superficie de mantenimiento o seguridad.

## 9.12 Límites de seguridad de v0.3.0

Las medidas definidas para v0.3.0 deberán interpretarse dentro del
alcance establecido para esta versión.

ABAPCompass no pretende proporcionar en esta versión:

- aislamiento para ejecución de código no confiable.
- análisis estático completo de código ABAP.
- validación mediante compilación contra un sistema SAP.
- detección exhaustiva de vulnerabilidades en código ABAP.
- protección específica para un servicio expuesto públicamente a
  Internet.
- autenticación, autorización ni gestión de permisos.
- garantías sobre la corrección de las respuestas generadas por los
  modelos.

La ausencia de estas capacidades es coherente con el alcance de v0.3.0 y
no deberá compensarse introduciendo durante la implementación
funcionalidades no previstas.

Cualquier evolución que implique exposición pública, acceso a sistemas
SAP, ejecución de código o tratamiento de información sensible requerirá
una nueva evaluación de seguridad y la definición de controles
adicionales.

# 10. Estrategia de pruebas

ABAPCompass v0.3.0 ampliará la estrategia de pruebas existente para cubrir
las nuevas responsabilidades introducidas por la selección dinámica de
modelos, las políticas de respuesta y la interfaz web.

Las pruebas deberán permitir validar la mayor parte del comportamiento
de la aplicación de forma rápida, reproducible y determinista, evitando
que la ejecución habitual de la suite dependa de la disponibilidad de un
modelo de inteligencia artificial real.

Las pruebas con Ollama y modelos reales complementarán esta estrategia,
pero no sustituirán las validaciones automatizadas basadas en
componentes controlados.

La estrategia distinguirá entre el comportamiento determinista
responsabilidad de ABAPCompass y el contenido no determinista generado por
los modelos de inteligencia artificial.

## 10.1 Objetivos

La estrategia de pruebas tendrá como objetivos principales:

- detectar regresiones en las capacidades existentes.
- validar el comportamiento del catálogo de modelos.
- comprobar la selección y resolución dinámica del modelo.
- verificar las políticas asociadas a la generación de código.
- comprobar el filtrado determinista de respuestas cuando corresponda.
- validar los contratos públicos de la API REST.
- comprobar los comportamientos relevantes de la interfaz web.
- verificar el tratamiento de errores.
- verificar la incorporación determinista del aviso de validación
  profesional.
- mantener pruebas deterministas independientes de la disponibilidad de
  Ollama siempre que la funcionalidad probada no requiera una
  integración real.
- complementar las pruebas automatizadas con pruebas manuales sobre los
  modelos reales.
- incorporar las validaciones automatizadas al proceso de integración
  continua.

La incorporación de una nueva funcionalidad deberá acompañarse de las
pruebas adecuadas a su responsabilidad y nivel dentro de la
arquitectura.

## 10.2 Pruebas unitarias del núcleo

Las pruebas unitarias del paquete `core` validarán sus componentes de
forma aislada, utilizando dependencias controladas cuando resulte
necesario.

Deberán cubrir, entre otros comportamientos:

- funcionamiento de `ModelCatalog`.
- obtención de modelos mediante su identificador.
- tratamiento de identificadores no soportados.
- información asociada a cada definición de modelo.
- correspondencia entre modelos y `codeSuggestionMode`.
- comportamiento de `AIProviderResolver`.
- selección del proveedor correspondiente.
- tratamiento de proveedores no resolubles.
- comportamiento de los casos de uso ante la selección dinámica del
  modelo.

Las pruebas del catálogo deberán comprobar que el modelo predeterminado
existe entre los modelos soportados.

También deberán verificar que las políticas definidas para los modelos
corresponden a la configuración prevista para v0.3.0.

Las pruebas unitarias del núcleo no deberán requerir la ejecución de
Ollama.

## 10.3 Utilización de StaticAIProvider

`StaticAIProvider` continuará utilizándose como implementación
controlada de `AIProvider` para aquellas pruebas que necesiten ejecutar
los casos de uso sin acceder a un modelo real.

Su comportamiento determinista permitirá conocer previamente la
respuesta esperada y distinguir los defectos de ABAPCompass de la
variabilidad propia de un modelo de lenguaje.

`StaticAIProvider` podrá utilizarse para comprobar:

- ejecución de los casos de uso.
- propagación de los resultados.
- colaboración entre los casos de uso y el proveedor.
- construcción de respuestas públicas.
- incorporación del modelo utilizado.
- incorporación de la política correspondiente.
- incorporación del aviso de validación profesional.
- tratamiento de errores simulados cuando resulte necesario.

Las pruebas realizadas con `StaticAIProvider` deberán respetar los
mismos contratos funcionales utilizados durante la ejecución normal.

Por tanto, cuando una operación requiera `modelId`, la prueba deberá
proporcionar un identificador válido aunque la generación final sea
realizada mediante un proveedor controlado.

`StaticAIProvider` no se incorporará al catálogo público ni se utilizará
como modelo seleccionable desde la interfaz web.

## 10.4 Pruebas de la API REST

Las pruebas de la aplicación `api` deberán validar los contratos HTTP
definidos en el capítulo 6.

La operación:

```text
GET /models
```

deberá comprobarse verificando, al menos:

- código de estado satisfactorio.
- tipo de contenido esperado.
- presencia de `defaultModelId`.
- presencia de la colección de modelos.
- exposición de los atributos públicos previstos.
- correspondencia de los modelos con el catálogo definido.
- ausencia de propiedades internas como `providerId` y
  `providerModel`.

La operación:

```text
GET /health
```

deberá comprobarse verificando el estado HTTP y la estructura de la
información de estado proporcionada por la API.

Las operaciones:

```text
POST /assistant/query
POST /assistant/explain
POST /assistant/review
```

deberán probarse con peticiones válidas e inválidas.

Las pruebas satisfactorias deberán comprobar, según corresponda:

- código HTTP esperado.
- presencia de `response`.
- identificación mediante `modelId` del modelo utilizado.
- presencia de `codeSuggestionMode`.
- presencia de `policy`.
- correspondencia de `policy.filtered` y, cuando proceda,
  `policy.reason` con el filtrado aplicado.
- presencia del aviso `validation`.
- estructura y valores deterministas proporcionados por ABAPCompass.

Las pruebas de error deberán cubrir los escenarios relevantes del
contrato, incluyendo:

- ausencia o contenido inválido de campos obligatorios.
- ausencia de `modelId`.
- identificador de modelo no soportado.
- proveedor no disponible.
- tiempo de espera agotado cuando pueda simularse de forma
  determinista.
- error interno.

Las respuestas de error deberán verificarse contra la estructura pública
formada por `code` y `message`, sin depender de detalles internos de las
excepciones.

## 10.5 Pruebas de la interfaz web

La interfaz web deberá disponer de pruebas automatizadas para aquella
lógica cuyo comportamiento pueda comprobarse de forma determinista sin
necesidad de reproducir una interacción completa con un navegador real.

Se priorizarán especialmente los comportamientos relacionados con la
interpretación y representación de las respuestas del asistente.

Las pruebas deberán comprobar, cuando corresponda:

- identificación de contenido textual.
- identificación de bloques de código delimitados.
- conservación del lenguaje asociado a un bloque de código cuando esté
  disponible.
- conservación del orden entre texto y código.
- reconocimiento del marcador correspondiente a un bloque eliminado por
  la política de respuesta.
- generación del segmento necesario para que la interfaz represente el
  aviso de contenido filtrado.
- conservación del resto del contenido cuando se haya producido
  filtrado.

Los comportamientos de integración de la interfaz con la API se
complementarán mediante pruebas manuales sobre la aplicación ejecutada.

Estas pruebas deberán comprobar especialmente:

- carga del catálogo de modelos.
- selección inicial mediante `defaultModelId`.
- cambio del modelo seleccionado.
- utilización de la selección en las tres capacidades.
- validación de los campos obligatorios.
- estado mostrado durante una operación.
- presentación de respuestas satisfactorias.
- presentación del aviso de validación profesional.
- representación de bloques de código.
- representación del aviso correspondiente a código omitido.
- presentación de errores.

La estrategia evitará incorporar herramientas o dependencias de testing
de interfaz cuya complejidad no esté justificada por el alcance de
v0.3.0.

## 10.6 Pruebas de integración

Las pruebas de integración verificarán la colaboración entre componentes
cuando el comportamiento relevante no pueda validarse adecuadamente
mediante una prueba unitaria aislada.

Deberán contemplarse escenarios como:

- recepción de `modelId` por la API y localización de su definición.
- resolución del `AIProvider` correspondiente.
- ejecución del caso de uso mediante un proveedor controlado.
- aplicación de la configuración asociada al modelo.
- transformación del resultado interno en la respuesta pública.
- aplicación de la política determinista de respuesta.
- incorporación determinista del aviso de validación profesional.
- traducción de errores internos al contrato HTTP.

Estas pruebas deberán utilizar `StaticAIProvider` o implementaciones
controladas siempre que el objetivo sea verificar la integración interna
de ABAPCompass y no la comunicación real con un proveedor de inteligencia
artificial.

## 10.7 Pruebas con Ollama y modelos reales

Además de las pruebas automatizadas deterministas, deberán realizarse
pruebas específicas con Ollama y los modelos reales previstos para
v0.3.0.

Estas pruebas tendrán como finalidad comprobar:

- disponibilidad real del modelo.
- compatibilidad del identificador configurado en `providerModel`.
- comunicación correcta con Ollama.
- funcionamiento de las tres capacidades principales.
- comportamiento observable de cada política de generación de código.
- aplicación de los controles deterministas de ABAPCompass cuando
  corresponda.
- presentación correcta de las respuestas mediante la interfaz web.
- tratamiento de errores cuando el servicio o el modelo no estén
  disponibles.

Antes de considerar completada la versión se realizará una ronda final
de pruebas con los tres modelos incluidos en el catálogo y las tres
operaciones principales.

Las respuestas de los modelos no se evaluarán mediante comparaciones
literales con un texto esperado debido a su naturaleza no determinista.

Las pruebas permitirán observar la calidad y la adherencia de las
respuestas a las instrucciones proporcionadas, pero una respuesta
incorrecta, una alucinación o una clasificación técnicamente discutible
del modelo no implicará por sí misma un defecto de ABAPCompass cuando la
aplicación haya aplicado correctamente sus contratos y controles.

La evaluación manual deberá distinguir entre:

- defectos funcionales de ABAPCompass.
- limitaciones o comportamiento no determinista del modelo utilizado.

Estas pruebas no formarán parte obligatoria de la ejecución ordinaria de
la suite automatizada mientras requieran Ollama, modelos instalados
localmente u otros recursos no disponibles en el entorno de CI.

## 10.8 Pruebas de las políticas de generación de código

Las políticas `none`, `snippets` y `full` deberán disponer de pruebas
específicas sobre el comportamiento controlado por ABAPCompass.

Deberán comprobarse las siguientes relaciones:

```text
Llama 3.2 3B
        |
        +-- none

Qwen 2.5 Coder 7B
        |
        +-- snippets

DeepSeek Coder V2 16B
        |
        +-- full
```

Las pruebas de la política preventiva deberán verificar que ABAPCompass
construye las instrucciones correspondientes a `codeSuggestionMode`
antes de realizar la petición al modelo.

Estas pruebas deberán validar el comportamiento controlado por ABAPCompass
y no intentar demostrar que un LLM cumplirá siempre las instrucciones
recibidas.

Las pruebas realizadas con modelos reales permitirán observar el grado
de adherencia a dichas instrucciones, pero ese comportamiento no se
considerará una garantía determinista proporcionada por ABAPCompass.

## 10.9 Pruebas de la política determinista de respuesta

La política aplicada a las respuestas cuando `codeSuggestionMode` sea
`none` deberá disponer de pruebas automatizadas independientes del
modelo de inteligencia artificial.

Como mínimo deberá comprobarse que:

- una respuesta sin bloques de código delimitados permanece sin
  modificar.
- `policy.filtered` es `false` cuando no se produce filtrado.
- un bloque de código delimitado es eliminado cuando la política es
  `none`.
- el texto anterior y posterior al bloque eliminado se conserva.
- la posición del bloque eliminado queda representada mediante el
  marcador interno correspondiente.
- `policy.filtered` es `true` cuando se produce filtrado.
- `policy.reason` contiene `CODE_SUGGESTION_NOT_ALLOWED` cuando se ha
  aplicado el filtrado.
- las políticas `snippets` y `full` no aplican este filtrado.
- el control no intenta clasificar mediante heurísticas el texto
  ordinario como código.

Las pruebas de la interfaz deberán verificar de forma independiente que
el marcador recibido puede transformarse en el segmento utilizado para
representar visualmente el aviso de código omitido.

De esta forma quedarán probadas por separado:

```text
API
 |
 +-- decide y aplica el filtrado
 |
 +-- proporciona metadatos y marcador
             |
             v
Interfaz
 |
 +-- interpreta el resultado
 |
 +-- representa el aviso al usuario
```

## 10.10 Pruebas del aviso de validación profesional

La incorporación del aviso de validación profesional deberá probarse
independientemente del contenido generado por el modelo.

Las pruebas deberán verificar que:

- todas las respuestas satisfactorias de las capacidades funcionales
  incluyen `validation`.
- `validation.title` y `validation.message` contienen los valores
  definidos por ABAPCompass.
- el aviso procede de ABAPCompass y no del proveedor de inteligencia
  artificial.
- el aviso no depende del modelo seleccionado.
- las respuestas de error no incorporan el aviso.

La representación del aviso mediante la interfaz se comprobará durante
las pruebas correspondientes de la aplicación web.

La prueba no deberá solicitar al modelo que genere el texto del aviso.

De esta forma podrá comprobarse determinísticamente una funcionalidad que
forma parte del contrato público de ABAPCompass.

## 10.11 Pruebas de regresión

Las pruebas existentes de v0.2.0 deberán mantenerse siempre que
continúen representando comportamientos válidos en v0.3.0.

Cuando un contrato haya cambiado deliberadamente, como ocurre con la
incorporación obligatoria de `modelId` o con la ampliación de la
respuesta pública, las pruebas correspondientes deberán actualizarse
para reflejar el nuevo comportamiento esperado.

No deberán eliminarse pruebas únicamente para conseguir que la suite
vuelva a ser satisfactoria.

Cuando una prueba deje de ser aplicable deberá revisarse si:

- representa un comportamiento que continúa siendo necesario.
- debe adaptarse al nuevo contrato.
- ha sido sustituida por otra prueba equivalente.
- corresponde realmente a una funcionalidad eliminada o modificada
  deliberadamente.

Los cambios realizados sobre pruebas existentes deberán formar parte de
los commits correspondientes a la funcionalidad que modifica su
comportamiento.

## 10.12 Cobertura de pruebas

La cobertura deberá utilizarse como indicador de las partes del código
ejercitadas por la suite, pero no como sustituto de la calidad de las
pruebas.

Se priorizará la cobertura de:

- reglas y comportamientos deterministas.
- validaciones.
- resolución de modelos y proveedores.
- política preventiva de generación.
- política determinista de respuesta.
- contratos de la API.
- lógica relevante de representación de la interfaz.
- aviso de validación profesional.
- tratamiento de errores.

No se establece como objetivo de v0.3.0 alcanzar un porcentaje
arbitrario de cobertura mediante pruebas sin valor funcional.

Cualquier umbral automatizado que se incorpore al proyecto deberá
establecerse de forma justificada y compatible con el estado real de la
base de código.

## 10.13 Integración con CI

La suite automatizada de v0.3.0 deberá formar parte del pipeline de
integración continua.

El pipeline deberá ejecutar las comprobaciones necesarias para detectar
errores antes de integrar cambios en el repositorio.

Las aplicaciones y componentes de v0.3.0 deberán quedar incorporados a
las validaciones existentes.

El proceso de CI deberá incluir las comprobaciones automatizadas
definidas por el proyecto para:

- formato.
- compilación.
- análisis estático.
- comprobación de tipos.
- pruebas automatizadas.
- construcción de las aplicaciones y paquetes correspondientes.

Las pruebas que dependan de Ollama o de modelos instalados localmente no
formarán parte obligatoria del pipeline general mientras el entorno de
CI no proporcione explícitamente dichos recursos.

El éxito del pipeline será una condición necesaria para considerar
validado un cambio antes de integrarlo en una versión.

## 10.14 Criterios de aceptación de las pruebas

La estrategia de pruebas de v0.3.0 se considerará aplicada correctamente
cuando:

- las funcionalidades nuevas dispongan de pruebas automatizadas
  adecuadas para su comportamiento determinista.
- las pruebas existentes hayan sido adaptadas cuando el contrato haya
  cambiado deliberadamente.
- las pruebas automatizadas puedan ejecutarse sin depender de Ollama
  salvo cuando se trate específicamente de una prueba de integración
  real.
- los contratos de la API estén cubiertos mediante pruebas
  satisfactorias y de error.
- el catálogo y la resolución dinámica de modelos estén cubiertos.
- la política preventiva de generación esté verificada.
- la política determinista de respuesta esté cubierta mediante pruebas
  automatizadas.
- el aviso de validación profesional esté cubierto de forma
  determinista.
- la lógica relevante de interpretación de respuestas de la interfaz
  disponga de pruebas automatizadas.
- se hayan realizado pruebas manuales de las capacidades principales de
  la interfaz.
- se haya realizado una ronda final con los tres modelos reales y las
  tres operaciones principales.
- las validaciones automatizadas requeridas por el proyecto finalicen
  satisfactoriamente.

# 11. CI/CD y control de calidad

ABAPCompass v0.3.0 mantendrá y ampliará las prácticas de integración
continua establecidas en la versión anterior para cubrir el conjunto de
componentes de la solución.

El objetivo será detectar de forma automatizada problemas de formato,
compilación, análisis estático, tipos, pruebas y construcción antes de
considerar válido un cambio.

La automatización deberá favorecer un proceso de desarrollo reproducible
y permitir que las mismas comprobaciones fundamentales puedan ejecutarse
tanto en el entorno local como en el entorno de integración continua.

El alcance de v0.3.0 no requiere el despliegue automático de ABAPCompass en
un entorno productivo.

## 11.1 Integración continua

La integración continua se realizará mediante GitHub Actions.

Los cambios publicados en el repositorio deberán someterse a las
validaciones automatizadas definidas por el proyecto.

Las aplicaciones `api` y `web`, junto con el paquete `core`, deberán
quedar incluidas en las comprobaciones generales cuando la validación
correspondiente resulte aplicable.

La configuración de integración continua permanecerá versionada junto
con el código fuente para que su evolución forme parte del historial del
proyecto.

El resultado de GitHub Actions proporcionará una comprobación
independiente del entorno local utilizado durante el desarrollo.

## 11.2 Validaciones automatizadas

El proceso de validación deberá ejecutar las comprobaciones automatizadas
definidas por el proyecto.

Como mínimo se contemplarán:

- comprobación del formato.
- compilación de los componentes que la requieran.
- análisis estático mediante las reglas configuradas.
- comprobación de tipos TypeScript.
- ejecución de las pruebas automatizadas.
- construcción de las aplicaciones y paquetes correspondientes.

Las comprobaciones deberán aplicarse al conjunto de componentes
relevantes del repositorio, incluyendo la aplicación web cuando sean
técnicamente pertinentes.

La incorporación de una nueva aplicación o paquete no deberá dejar
partes relevantes del repositorio fuera de las comprobaciones
automatizadas.

## 11.3 Validación local

Las comprobaciones fundamentales deberán poder ejecutarse también desde
el entorno local de desarrollo.

El proyecto mantendrá scripts que permitan ejecutar de forma
reproducible las validaciones necesarias sin depender exclusivamente de
GitHub Actions.

La validación general podrá ejecutarse mediante el script definido por
el proyecto para este propósito, integrando las diferentes
comprobaciones automatizadas.

Cuando resulte posible, la validación local y la ejecutada por CI
utilizarán los mismos comandos o scripts del proyecto.

Esto permitirá detectar problemas antes de publicar los cambios y
reducirá las diferencias entre el comportamiento observado localmente y
el obtenido en el pipeline.

La aplicación `web` formará parte de los mecanismos de validación
general correspondientes.

## 11.4 Construcción del proyecto

El proceso de construcción deberá comprobar que los componentes que
requieran generación de artefactos compilados pueden construirse
correctamente.

La interfaz web deberá poder construirse correctamente mediante los
mecanismos definidos por el proyecto.

La construcción no deberá depender de la disponibilidad de Ollama ni de
la ejecución de modelos de inteligencia artificial.

Los parámetros que puedan variar entre entornos deberán gestionarse
mediante los mecanismos de configuración definidos para el proyecto y no
mediante modificaciones manuales del código fuente.

## 11.5 Dependencias

Las dependencias del proyecto deberán declararse mediante los mecanismos
de gestión de paquetes utilizados por el repositorio.

Los archivos de bloqueo de dependencias deberán mantenerse versionados
cuando formen parte de la estrategia utilizada por el proyecto.

La instalación utilizada por CI deberá ser reproducible a partir de la
información almacenada en el repositorio.

La incorporación o actualización de una dependencia deberá realizarse de
forma explícita y quedar reflejada en el historial de cambios.

Las dependencias de `apps/web` deberán limitarse a las necesarias para
implementar, probar y construir la interfaz definida para v0.3.0.

## 11.6 Gestión de errores del pipeline

Un fallo en una validación obligatoria deberá provocar que la ejecución
correspondiente del pipeline se considere fallida.

Los errores deberán corregirse en el código, configuración o pruebas que
los originen.

No deberán desactivarse validaciones ni eliminarse pruebas únicamente
para obtener una ejecución satisfactoria.

Cuando un cambio deliberado modifique un comportamiento existente, las
pruebas y configuraciones afectadas deberán actualizarse de forma
coherente con el nuevo comportamiento esperado.

Los resultados proporcionados por GitHub Actions servirán como evidencia
adicional de que los cambios publicados han superado las comprobaciones
automatizadas definidas por el proyecto.

## 11.7 Independencia de los modelos de inteligencia artificial

La ejecución ordinaria del pipeline no dependerá de la disponibilidad de
Ollama ni de modelos de inteligencia artificial instalados localmente.

Las pruebas automatizadas que requieran una implementación de
`AIProvider` utilizarán `StaticAIProvider` u otras implementaciones
controladas cuando el objetivo no sea validar específicamente la
integración con un proveedor real.

Las pruebas con Ollama y modelos reales se ejecutarán separadamente
cuando corresponda, de acuerdo con la estrategia definida en el capítulo 10.

Esta separación evitará que la disponibilidad, el tiempo de respuesta o
la variabilidad de un modelo de inteligencia artificial determine el
resultado de las validaciones ordinarias del repositorio.

## 11.8 Control de calidad del código

Además de las pruebas automatizadas, el proyecto mantendrá mecanismos
orientados a preservar la calidad y consistencia del código.

Estos mecanismos incluirán:

- formato automático y comprobación del formato.
- análisis estático.
- comprobación de tipos.
- pruebas automatizadas.
- construcción satisfactoria.
- revisión de los cambios antes de considerarlos completados.

Las reglas comunes deberán aplicarse de forma coherente a los
componentes del repositorio siempre que las tecnologías utilizadas lo
permitan.

Las excepciones a las reglas generales deberán introducirse únicamente
cuando exista una justificación técnica.

El control de calidad no se limitará al resultado de una única
herramienta. La aceptación de un cambio dependerá del conjunto de
comprobaciones aplicables y de la revisión de su comportamiento.

## 11.9 Evolución del pipeline

El pipeline evolucionará junto con las funcionalidades del proyecto.

Cuando un incremento introduzca código que requiera una nueva
validación, el pipeline deberá adaptarse dentro del mismo proceso de
desarrollo.

La incorporación de la interfaz web implica que deberán quedar
contemplados, cuando corresponda:

- instalación de sus dependencias.
- comprobación de tipos.
- análisis estático.
- ejecución de sus pruebas automatizadas.
- construcción de la aplicación.

Las modificaciones del pipeline deberán realizarse de forma incremental
y quedar versionadas junto con el resto de los cambios.

De esta forma, la integración continua evolucionará junto con el código
y permitirá detectar problemas durante el desarrollo de cada incremento.

## 11.10 Entrega continua

Las prácticas de entrega continua de v0.3.0 estarán orientadas a
mantener el repositorio en un estado validado y reproducible que permita
preparar e identificar las versiones de ABAPCompass.

No se implementará un proceso de despliegue automático en
infraestructura productiva.

La preparación de una versión requerirá que:

- las validaciones automatizadas obligatorias finalicen
  satisfactoriamente.
- las pruebas específicas que no formen parte de CI hayan sido
  realizadas cuando correspondan.
- la documentación asociada a la versión esté actualizada.
- los cambios previstos para la versión hayan sido completados.
- no existan errores conocidos que impidan satisfacer sus criterios de
  aceptación.

Las pruebas con Ollama y los modelos reales previstas para el cierre de
v0.3.0 formarán parte de las comprobaciones específicas realizadas fuera
del pipeline ordinario.

La identificación de una versión en el repositorio se realizará
únicamente después de verificar las condiciones establecidas para su
cierre.

## 11.11 Trazabilidad de los cambios

Los cambios realizados durante el desarrollo deberán quedar reflejados
en el historial de Git.

Los commits deberán representar unidades de cambio comprensibles y
utilizar mensajes que permitan identificar razonablemente su finalidad.

Las modificaciones de código deberán incluir, cuando corresponda, las
pruebas y cambios de configuración necesarios para validarlas.

La evolución de v0.3.0 deberá permitir relacionar las funcionalidades
incorporadas con los cambios realizados en el repositorio y con el

El repositorio remoto proporcionará además evidencia del estado de las
ejecuciones de integración continua asociadas a los cambios publicados.

Esta trazabilidad formará parte de las evidencias del proceso de

## 11.12 Cierre y versionado

La identificación formal de v0.3.0 se realizará una vez completadas las
funcionalidades previstas para la versión y satisfechas sus condiciones
de aceptación.

Antes de realizar este cierre deberán comprobarse:

- el estado satisfactorio de las validaciones automatizadas.

- la coherencia entre la implementación y la documentación.
- la actualización de la información activa de versión que corresponda.

La actualización del número de versión formará parte del proceso de

versiones anteriores.

Después de actualizar la información de versión deberán ejecutarse
nuevamente las validaciones necesarias y comprobar que el estado
destinado a v0.3.0 continúa siendo satisfactorio.

Una vez que el commit correspondiente al estado final de la versión haya
superado satisfactoriamente las comprobaciones previstas, se identificará
mediante el tag Git:

`v0.3.0`

El tag se asociará al commit validado y se publicará en el repositorio
remoto.

De esta forma, v0.3.0 quedará identificada mediante el mismo mecanismo
utilizado para las versiones anteriores del proyecto.

## 11.13 Criterios de aceptación del proceso CI/CD

El proceso de CI/CD de v0.3.0 se considerará correctamente aplicado

- la aplicación web pueda construirse mediante los mecanismos

- las pruebas ordinarias no dependan de Ollama ni de modelos

- los fallos de las validaciones impidan considerar satisfactorio el
  cambio.
- la configuración del pipeline permanezca versionada.
- las pruebas manuales previstas para el cierre hayan sido realizadas.
- la documentación y la implementación sean coherentes.
- la preparación e identificación de la versión se realicen a partir de
  un estado validado del repositorio.

# 12. Plan de implementación

La implementación de ABAPCompass v0.3.0 se realizará de forma incremental,
partiendo del estado validado y publicado de v0.2.0.

Cada incremento incorporará una responsabilidad concreta y deberá
mantener el proyecto en un estado coherente y verificable antes de
abordar el siguiente.

El orden de implementación seguirá las dependencias definidas por la
arquitectura. Las funcionalidades del núcleo se desarrollarán antes que
los contratos que dependan de ellas y la interfaz web se construirá
sobre una API previamente definida y validada.

La secuencia descrita en este capítulo podrá ajustarse durante el
desarrollo cuando aparezca una necesidad técnica justificada, siempre
que no se alteren sin revisión previa las responsabilidades y contratos
establecidos en este documento.

## 12.1 Preparación de la versión

El desarrollo de v0.3.0 comenzará a partir del estado correspondiente al
cierre de v0.2.0.

Antes de incorporar nuevas funcionalidades se comprobará que:

- el repositorio se encuentra en el estado esperado.
- las dependencias pueden instalarse correctamente.
- las validaciones locales existentes finalizan satisfactoriamente.
- el pipeline de integración continua se encuentra operativo.
- la documentación de diseño de v0.3.0 está disponible como referencia
  para la implementación.

La nueva versión se desarrollará sin modificar retrospectivamente el
contenido funcional de v0.2.0.

## 12.2 Incorporación del catálogo de modelos

El primer incremento funcional introducirá la representación de los
modelos soportados mediante `ModelCatalog` y las definiciones asociadas.

Este incremento deberá proporcionar:

- la estructura necesaria para representar una definición de modelo.
- los modelos soportados inicialmente por v0.3.0.
- el identificador del modelo predeterminado.
- la política `codeSuggestionMode` asociada a cada modelo.
- las operaciones necesarias para obtener el catálogo.
- la localización de una definición mediante su identificador.
- el tratamiento controlado de identificadores no soportados.

La implementación deberá acompañarse de pruebas unitarias que permitan
validar el catálogo sin acceder a un proveedor de inteligencia
artificial.

En este incremento todavía no será necesario modificar la interfaz web.

## 12.3 Resolución dinámica de proveedores

Una vez disponible el catálogo se incorporará el mecanismo necesario
para resolver el proveedor correspondiente al modelo seleccionado.

Durante la ejecución de cada caso de uso, la definición del modelo
obtenida desde `ModelCatalog` se proporcionará a `AIProviderResolver`,
que determinará la implementación de `AIProvider` que deberá participar
en la operación.

La implementación deberá mantener los casos de uso desacoplados de
proveedores concretos.

Este incremento deberá cubrir:

- resolución a partir de una definición de modelo válida.
- utilización de la configuración asociada al modelo.
- tratamiento de errores de resolución.
- compatibilidad con `OllamaAIProvider`.
- posibilidad de utilizar `StaticAIProvider` en pruebas sin
  incorporarlo al catálogo público.

La resolución deberá disponer de pruebas deterministas independientes de
la disponibilidad de Ollama.

## 12.4 Adaptación de los casos de uso

Los casos de uso existentes deberán evolucionar para ejecutar cada
operación utilizando el modelo solicitado.

Las capacidades afectadas serán:

```text
query
explain
review
```

La adaptación deberá preservar la separación entre lógica de aplicación
y detalles específicos de los proveedores.

Los casos de uso recibirán la información necesaria para identificar el
modelo de la operación y utilizarán los mecanismos definidos por el
núcleo para obtener la configuración y el proveedor correspondientes.

En este incremento también se integrará `codeSuggestionMode` en las
instrucciones construidas para cada operación cuando corresponda.

Estas instrucciones constituirán un control preventivo destinado a
orientar el comportamiento del modelo y no una garantía de cumplimiento.

Las pruebas existentes deberán actualizarse cuando el nuevo contrato
interno modifique deliberadamente su comportamiento.

## 12.5 Evolución de la API REST

Una vez estabilizada la selección dinámica en el núcleo, se adaptará la
aplicación `api`.

Se incorporará:

```text
GET /models
```

para proporcionar el catálogo público y el modelo predeterminado.

También se modificarán:

```text
POST /assistant/query
POST /assistant/explain
POST /assistant/review
```

para requerir `modelId`.

La implementación deberá garantizar que los contratos HTTP no permitan
seleccionar directamente proveedores, identificadores técnicos de
modelos ni parámetros internos de configuración.

Las respuestas satisfactorias incorporarán la identificación pública del
modelo utilizado y la información correspondiente a su política de
generación de código.

En este incremento se actualizarán las pruebas de API para cubrir tanto
las respuestas satisfactorias como los nuevos escenarios de error.

## 12.6 Incorporación del aviso de validación profesional

Las respuestas satisfactorias de las capacidades funcionales se
ampliarán para incorporar el aviso de validación profesional definido
para v0.3.0.

El aviso será añadido por ABAPCompass y no será solicitado al modelo de
inteligencia artificial.

La implementación deberá garantizar que:

- el texto sea independiente del modelo utilizado.
- todas las capacidades funcionales lo incorporen de forma consistente.
- las respuestas de error no lo incorporen.
- el comportamiento pueda comprobarse mediante pruebas deterministas.

La incorporación del aviso se realizará en el backend para que forme
parte del contrato público con independencia del cliente utilizado para
acceder a ABAPCompass.

## 12.7 Incorporación de la política determinista de respuesta

Además de las instrucciones preventivas asociadas a
`codeSuggestionMode`, se incorporará un control determinista sobre las
respuestas cuando la política sea `none`.

Este control deberá:

- actuar sobre la respuesta antes de exponerla mediante la API.
- identificar bloques de código delimitados estructuralmente.
- eliminar únicamente los bloques identificados cuando la política sea
  `none`.
- conservar el resto del contenido generado.
- mantener la posición del contenido eliminado mediante un marcador
  interno.
- proporcionar metadatos que permitan conocer si se ha producido
  filtrado.
- proporcionar un motivo estable cuando corresponda.

El control no intentará identificar como código fragmentos incluidos
dentro del texto ordinario de la respuesta.

La política deberá disponer de pruebas automatizadas independientes del
comportamiento de los modelos de inteligencia artificial.

## 12.8 Preparación de la aplicación web

Una vez que los contratos necesarios de la API estén disponibles y
probados, se preparará `apps/web`.

La aplicación utilizará Vite, TypeScript, HTML y CSS nativos, sin
incorporar un framework de interfaz adicional.

Este incremento incluirá únicamente la infraestructura mínima necesaria
para comenzar el desarrollo de la interfaz, incluyendo:

- configuración de la aplicación.
- integración con los scripts generales del proyecto.
- comprobación de tipos.
- análisis estático cuando corresponda.
- ejecución de las pruebas aplicables.
- construcción de la aplicación.

La incorporación de dependencias adicionales deberá limitarse a las
necesarias para el alcance definido.

## 12.9 Estructura general de la interfaz

Sobre la aplicación web preparada se implementará la estructura común de
la interfaz.

Este incremento incluirá:

- identificación de ABAPCompass.
- navegación entre las áreas funcionales.
- página de inicio.
- estructura común de presentación.
- acceso a la API.
- tratamiento básico de estados de carga y error.

La implementación deberá permitir incorporar posteriormente las
capacidades funcionales sin duplicar innecesariamente comportamiento
común.

## 12.10 Selector de modelos

El siguiente incremento incorporará la selección de modelos.

La interfaz obtendrá los modelos exclusivamente mediante:

```text
GET /models
```

y utilizará `defaultModelId` para establecer la selección inicial.

El incremento deberá implementar:

- carga del catálogo.
- presentación de los modelos disponibles.
- presentación de su descripción.
- presentación comprensible de `codeSuggestionMode`.
- selección inicial del modelo predeterminado.
- cambio de modelo por parte del usuario.
- mantenimiento de la selección entre las distintas áreas funcionales.
- tratamiento del error cuando el catálogo no pueda obtenerse.

La interfaz no mantendrá una definición independiente del catálogo ni
del modelo predeterminado.

## 12.11 Implementación del Asistente SAP

La primera capacidad funcional incorporada a la interfaz será Asistente
SAP.

La implementación deberá permitir:

- introducir una consulta.
- proporcionar contexto adicional cuando sea necesario.
- validar los datos obligatorios.
- enviar el `modelId` seleccionado.
- representar el estado de procesamiento.
- mostrar la respuesta recibida.
- identificar el modelo utilizado.
- mostrar la política aplicada.
- mostrar el aviso de validación profesional.
- representar el contenido omitido por la política de respuesta cuando
  corresponda.
- presentar los errores de forma comprensible.

Los comportamientos deterministas que puedan aislarse razonablemente
deberán quedar cubiertos mediante las pruebas correspondientes.

## 12.12 Implementación de Explicación ABAP

A continuación se incorporará la capacidad Explicación ABAP.

La implementación deberá permitir:

- introducir código ABAP.
- proporcionar contexto adicional.
- preservar el formato del código.
- enviar el `modelId` seleccionado.
- representar el estado de procesamiento.
- mostrar la explicación generada.
- representar adecuadamente los fragmentos de código presentes en la
  respuesta.
- identificar el modelo y la política utilizados.
- mostrar el aviso de validación profesional.
- representar el contenido omitido por la política de respuesta cuando
  corresponda.
- tratar los errores definidos por la API.

La funcionalidad reutilizará comportamientos comunes cuando ello evite
duplicación sin introducir abstracciones innecesarias.

El código introducido y el contenido generado se tratarán como datos y
no se insertarán como HTML interpretable.

## 12.13 Implementación de Revisión ABAP

La tercera capacidad incorporada será Revisión ABAP.

La implementación deberá permitir:

- introducir código ABAP.
- proporcionar contexto adicional.
- enviar el `modelId` seleccionado.
- representar el estado de procesamiento.
- presentar la revisión generada.
- diferenciar visualmente las explicaciones de los bloques de código
  cuando corresponda.
- identificar el modelo y la política utilizados.
- mostrar el aviso de validación profesional.
- representar el contenido omitido por la política de respuesta cuando
  corresponda.
- tratar adecuadamente los errores.

La interfaz no presentará el resultado como una validación equivalente a
una compilación, ejecución o análisis realizado sobre un sistema SAP.

## 12.14 Integración de la interfaz y la API

Una vez implementadas las tres capacidades se validará conjuntamente la
comunicación entre `web` y `api`.

Esta fase deberá comprobar:

- obtención real del catálogo.
- selección del modelo predeterminado.
- cambio de modelo.
- envío correcto de `modelId`.
- ejecución de las tres capacidades.
- representación de las respuestas satisfactorias.
- representación del aviso de validación profesional.
- representación del contenido omitido por la política de respuesta.
- tratamiento de errores HTTP.
- comportamiento cuando la API no esté disponible.

La integración deberá mantener la separación de responsabilidades
definida en la arquitectura: la API decidirá y aplicará el filtrado
correspondiente y la interfaz será responsable de representar el
resultado recibido.

Las pruebas de esta fase deberán distinguir los defectos de integración
entre las aplicaciones de la variabilidad propia de los modelos de
inteligencia artificial.

## 12.15 Validación con Ollama

Una vez validada la integración interna se realizarán pruebas con Ollama
y los modelos configurados para v0.3.0.

Se comprobará cada modelo mediante escenarios representativos de las
capacidades disponibles.

La validación deberá permitir confirmar:

- que los identificadores técnicos configurados son correctos.
- que cada modelo puede ser invocado mediante el proveedor.
- que la selección realizada desde la interfaz alcanza el modelo
  esperado.
- que las tres capacidades pueden ejecutarse correctamente.
- que las políticas preventivas producen un comportamiento
  razonablemente coherente con su finalidad.
- que el control determinista asociado a la política `none` se aplica
  cuando corresponda.
- que los errores de disponibilidad se gestionan de forma controlada.

Las respuestas generadas se revisarán manualmente cuando sea necesario
evaluar su calidad técnica.

Una respuesta técnicamente incorrecta, una alucinación o una
clasificación no justificada producida por el modelo no constituirá por
sí misma un defecto de ABAPCompass cuando la aplicación haya aplicado
correctamente sus contratos y controles.

La validación con modelos reales no sustituirá las pruebas automatizadas
deterministas.

## 12.16 Adaptación de CI

La integración continua evolucionará junto con los incrementos
anteriores.

Cuando se incorpore `apps/web`, las validaciones generales deberán
ampliarse para cubrir la nueva aplicación.

Antes del cierre de v0.3.0 deberá comprobarse que el pipeline incluye

# 13. Estrategia de versionado y Git

El desarrollo de ABAPCompass v0.3.0 se realizará mediante cambios
incrementales versionados con Git y publicados progresivamente en el
repositorio remoto.

Aunque Git y GitHub ya se han utilizado durante el desarrollo de
versiones anteriores, v0.3.0 documenta explícitamente los criterios
generales que se seguirán durante la evolución de esta versión.

La estrategia tendrá como finalidad mantener un historial comprensible,
facilitar la trazabilidad de los cambios y conservar puntos de
recuperación durante el desarrollo.

La versión no se implementará mediante un único cambio al finalizar el
desarrollo. Las funcionalidades, correcciones, pruebas, documentación y
adaptaciones de configuración se incorporarán progresivamente cuando
alcancen un estado coherente y validable.

## 13.1 Rama de desarrollo

El desarrollo ordinario de v0.3.0 se realizará sobre la rama `develop`.

Esta rama contendrá la evolución progresiva de la versión mientras
permanezca en desarrollo.

Los cambios publicados quedarán sometidos a las comprobaciones
automatizadas configuradas mediante GitHub Actions.

No se considera necesario introducir para v0.3.0 una estrategia de ramas
más compleja mientras las necesidades del proyecto no lo requieran.

## 13.2 Desarrollo incremental

Los cambios se incorporarán mediante incrementos suficientemente
pequeños para poder comprender, validar y revisar su finalidad.

Un incremento podrá incluir, según corresponda:

- implementación de una nueva funcionalidad.
- adaptación de una funcionalidad existente.
- pruebas asociadas.
- modificaciones necesarias de configuración.
- actualización de la documentación relacionada.
- correcciones detectadas durante la validación.

Los incrementos definidos en el plan de implementación del capítulo 12
no determinarán necesariamente la existencia de un único commit para
cada uno.

Cuando una funcionalidad requiera varios cambios claramente
diferenciados, podrá dividirse en varios commits.

## 13.3 Contenido de los commits

Los commits deberán representar unidades coherentes de cambio y permitir
identificar razonablemente su finalidad.

Siempre que resulte apropiado, un cambio que introduzca o modifique
comportamiento deberá incorporar las pruebas necesarias para
verificarlo.

Se evitará mezclar en un mismo commit modificaciones independientes que
dificulten comprender el cambio realizado.

Los cambios exclusivamente documentales, de configuración, pruebas o
mantenimiento podrán disponer de commits específicos cuando constituyan
una unidad de cambio independiente.

## 13.4 Mensajes de commit

Los mensajes de commit deberán describir de forma breve y comprensible
la finalidad principal del cambio.

Se mantendrá un criterio consistente durante el desarrollo, evitando
mensajes genéricos que no permitan identificar razonablemente el
contenido del commit.

No se establece en este documento una convención obligatoria de prefijos
o una estructura específica para los mensajes.

Los mensajes concretos se determinarán durante la implementación de
acuerdo con el contenido real de cada cambio.

## 13.5 Validación y publicación de cambios

Antes de publicar un incremento en el repositorio remoto se ejecutarán

su publicación.

remoto para:

# 14. Criterios de aceptación de v0.3.0

ABAPCompass v0.3.0 se considerará completado cuando las funcionalidades,
restricciones y condiciones de calidad definidas para la versión hayan
sido implementadas y verificadas.

Los criterios establecidos en este capítulo permitirán determinar de
forma objetiva si la versión puede considerarse finalizada.

El cumplimiento de estos criterios deberá evaluarse sobre el estado del
proyecto destinado al cierre de v0.3.0.

## 14.1 Catálogo de modelos

El catálogo de modelos se considerará correctamente implementado cuando:

- ABAPCompass disponga de un catálogo con los modelos soportados por
  v0.3.0.
- cada modelo disponga de un identificador propio utilizado por
  ABAPCompass.
- cada definición contenga la información necesaria para presentar el
  modelo, resolver su proveedor y aplicar su política de generación de
  código.
- exista un modelo predeterminado válido.
- el modelo predeterminado forme parte del catálogo.
- un identificador que no pertenezca al catálogo sea rechazado de
  forma controlada.
- el catálogo no permita seleccionar modelos arbitrarios no
  contemplados por la aplicación.
- las propiedades internas necesarias para acceder a los proveedores
  no se expongan innecesariamente mediante el contrato público.

## 14.2 Selección y resolución de modelos

La selección dinámica se considerará correctamente implementada cuando:

- cada operación funcional pueda indicar el modelo que deberá
  utilizar.
- el identificador recibido sea validado contra `ModelCatalog`.
- la definición correspondiente permita determinar el proveedor y la
  configuración necesarios.
- los casos de uso permanezcan desacoplados de proveedores concretos.
- un modelo no soportado produzca un error controlado.
- la selección realizada por el cliente no permita proporcionar
  directamente nombres técnicos de modelos, proveedores ni parámetros
  internos de infraestructura.

La utilización de `StaticAIProvider` para pruebas no implicará su
exposición como modelo seleccionable mediante el catálogo público.

## 14.3 Políticas de generación de código

Las políticas de generación se considerarán correctamente incorporadas
cuando:

- cada modelo del catálogo tenga asociada una política
  `codeSuggestionMode`.
- se soporten los modos `none`, `snippets` y `full` definidos para
  v0.3.0.
- la política aplicable se determine a partir de la definición del
  modelo y no a partir de un valor proporcionado libremente por el
  cliente.
- las instrucciones enviadas al modelo reflejen la política
  correspondiente.
- la política aplicada pueda identificarse en la respuesta pública.
- existan pruebas deterministas sobre el comportamiento controlado por
  ABAPCompass.

Las instrucciones proporcionadas al modelo constituirán un control
preventivo destinado a orientar su comportamiento.

No será requisito de aceptación demostrar que un modelo de lenguaje
cumplirá de forma absoluta las instrucciones recibidas.

Cuando `codeSuggestionMode` sea `none`, se considerará además requisito
de aceptación que ABAPCompass aplique un control determinista sobre la
respuesta antes de exponerla mediante la API.

Este control deberá:

- identificar bloques de código delimitados estructuralmente.
- eliminar únicamente los bloques identificados.
- conservar el resto del contenido de la respuesta.
- mantener la posición del contenido eliminado mediante el marcador
  definido para este propósito.
- indicar mediante metadatos que se ha producido el filtrado.
- proporcionar el motivo correspondiente cuando se haya aplicado.

El control no intentará identificar como código fragmentos incluidos
dentro del texto ordinario de la respuesta.

Las políticas `snippets` y `full` no aplicarán este filtrado
determinista.

## 14.4 API REST

La evolución de la API se considerará completada cuando:

- `GET /models` proporcione el catálogo público necesario para los
  clientes.
- `GET /models` proporcione `defaultModelId`.
- las operaciones `query`, `explain` y `review` requieran `modelId`.
- las peticiones válidas sean procesadas mediante el modelo
  solicitado.
- la ausencia de `modelId` produzca un error controlado.
- un `modelId` no soportado produzca un error controlado.
- las respuestas satisfactorias incluyan `response`.
- las respuestas satisfactorias identifiquen mediante `modelId` el
  modelo utilizado.
- las respuestas satisfactorias incluyan `codeSuggestionMode`.
- las respuestas satisfactorias incluyan la estructura `policy`.
- `policy.filtered` permita conocer si ABAPCompass ha eliminado contenido
  de la respuesta.
- `policy.reason` proporcione el motivo correspondiente cuando se haya
  aplicado el filtrado.
- las respuestas satisfactorias incluyan la estructura `validation`.
- las respuestas de error respeten el contrato definido y no expongan
  información interna innecesaria.
- las operaciones dispongan de pruebas automatizadas satisfactorias y
  de error.

## 14.5 Aviso de validación profesional

El aviso de validación profesional se considerará correctamente
incorporado cuando:

- todas las respuestas satisfactorias de las capacidades funcionales
  lo incluyan.
- sea incorporado por ABAPCompass y no generado por el modelo de
  inteligencia artificial.
- su presencia sea independiente del modelo seleccionado.
- el texto utilizado corresponda al definido para v0.3.0.
- se proporcione mediante la estructura `validation` del contrato
  público.
- las respuestas de error no lo incorporen.
- la interfaz web lo muestre de forma visible junto con las respuestas
  satisfactorias.
- su incorporación disponga de pruebas automatizadas deterministas.

El aviso no deberá interpretarse como sustitución de las medidas
técnicas de seguridad ni de la validación profesional de las respuestas.

## 14.6 Interfaz web

La interfaz web se considerará funcionalmente completada cuando:

- pueda iniciarse mediante los mecanismos definidos por el proyecto.
- pueda comunicarse con la API REST de ABAPCompass.
- proporcione acceso a Asistente SAP.
- proporcione acceso a Explicación ABAP.
- proporcione acceso a Revisión ABAP.
- obtenga el catálogo de modelos mediante la API.
- seleccione inicialmente el modelo indicado mediante
  `defaultModelId`.
- permita al usuario cambiar el modelo seleccionado.
- mantenga la selección al cambiar entre las distintas áreas
  funcionales mientras la aplicación permanezca activa.
- presente información comprensible sobre el modelo y su política de
  generación.
- envíe el `modelId` seleccionado en las operaciones funcionales.
- represente adecuadamente los estados de procesamiento.
- represente de forma comprensible los errores recibidos.
- muestre el modelo utilizado en las respuestas satisfactorias.
- muestre la política aplicada.
- muestre el aviso de validación profesional.
- represente adecuadamente los bloques de código permitidos.
- represente mediante un aviso explícito la posición del contenido
  eliminado por la política de respuesta.
- no acceda directamente a proveedores de inteligencia artificial.

La interfaz será responsable de representar el resultado del filtrado,
pero no de decidir qué contenido debe ser eliminado. Esta decisión
corresponderá a la API.

## 14.7 Usabilidad y accesibilidad

La interfaz se considerará adecuada para el alcance de v0.3.0 cuando:

- las tres capacidades principales puedan localizarse claramente.
- el modelo seleccionado sea identificable por el usuario.
- la política de generación asociada pueda comprenderse sin necesidad
  de conocer su representación interna.
- los campos obligatorios puedan identificarse.
- los estados de procesamiento y error sean perceptibles.
- las acciones principales puedan realizarse mediante teclado sin
  requerir el uso del ratón.
- la estructura de la interfaz utilice elementos y etiquetas adecuados
  para su función.
- el código ABAP conserve un formato que permita su lectura.
- el aviso de validación profesional resulte visible sin confundirse
  con la respuesta generada.
- el aviso correspondiente a contenido filtrado pueda distinguirse del
  contenido generado por el modelo.

No será requisito de v0.3.0 alcanzar una certificación formal de
accesibilidad.

## 14.8 Seguridad

Los requisitos de seguridad de la versión se considerarán satisfechos
cuando:

- las entradas recibidas por la API sean validadas.
- la validación del frontend no sustituya la validación del backend.
- `modelId` sea validado contra el catálogo antes de utilizarse.
- el cliente no pueda determinar directamente el proveedor ni su
  configuración interna.
- las credenciales y secretos no formen parte del código fuente ni del
  frontend.
- los datos sensibles de configuración no se expongan mediante las
  respuestas públicas.
- los errores públicos no incluyan trazas ni información interna
  innecesaria.
- el contenido recibido del usuario y de los modelos sea considerado no
  confiable.
- la interfaz represente el contenido no confiable sin insertarlo como
  HTML interpretable.
- ABAPCompass no ejecute automáticamente código proporcionado por el
  usuario.
- ABAPCompass no ejecute código ni acciones propuestas en las respuestas
  generadas por los modelos.
- la política determinista de respuesta se aplique en el backend cuando
  corresponda.
- la interfaz web acceda a las capacidades exclusivamente mediante la
  API REST.

Los criterios deberán interpretarse dentro de los límites de seguridad
establecidos para v0.3.0.

La estrategia de pruebas se considerará satisfactoriamente aplicada

Las respuestas de los modelos reales no deberán evaluarse mediante

Las pruebas deberán permitir diferenciar los defectos funcionales de
ABAPCompass de la variabilidad o las limitaciones propias del modelo

## 14.11 Integración con modelos reales

La integración con los modelos previstos para v0.3.0 se considerará

- los modelos necesarios estén disponibles en el entorno utilizado

  controles deterministas aplicados por ABAPCompass.
- incluya la información necesaria para configurar, iniciar y validar
  la aplicación.
- incluya una referencia clara de los endpoints y contratos públicos de
  la API.
- refleje las limitaciones relevantes de la versión.
- no describa como disponibles funcionalidades que hayan quedado fuera
  del alcance final.
- sea coherente con el comportamiento observable del software.

## 14.13 Criterio de cierre

ABAPCompass v0.3.0 podrá considerarse funcionalmente completado cuando los
criterios aplicables de este capítulo hayan sido comprobados
satisfactoriamente y no existan defectos conocidos que impidan cumplir
el alcance definido para la versión.

El cierre requerirá además:

- estado validado del repositorio.
- validaciones automatizadas satisfactorias.
- pruebas con modelos reales completadas según lo previsto.
- interfaz web funcional para las tres capacidades.
- documentación alineada con la implementación.
- revisión final del conjunto de cambios.

Una vez satisfechas estas condiciones se actualizará de forma controlada
la información activa de versión desde `0.2.0` a `0.3.0`.

Después de esta actualización deberán ejecutarse nuevamente las
validaciones aplicables y comprobarse satisfactoriamente la integración
continua sobre el estado destinado a la versión.

Solo después de completar estas comprobaciones se creará y publicará el
tag Git `v0.3.0` sobre el commit validado, quedando formalmente cerrada
la versión.

# 15. Limitaciones y evolución futura

ABAPCompass v0.3.0 amplía las capacidades de la versión anterior mediante
la selección dinámica de modelos y la incorporación de una interfaz web,
pero mantiene deliberadamente un alcance limitado.

Las restricciones descritas en este capítulo forman parte de las
decisiones adoptadas para mantener la versión abordable, verificable y
coherente con los objetivos del proyecto.

Algunas de estas limitaciones podrán abordarse en versiones posteriores.
Las posibles líneas de evolución indicadas no constituyen compromisos
para una versión concreta ni forman parte de los criterios de aceptación
de v0.3.0.

## 15.1 Catálogo estático de modelos

El catálogo de modelos de v0.3.0 será estático y estará definido por la
propia aplicación.

El usuario podrá seleccionar únicamente los modelos previamente
contemplados por ABAPCompass.

La versión no proporcionará mecanismos para:

- añadir modelos desde la interfaz web.
- modificar las definiciones existentes desde la interfaz web.
- eliminar modelos desde la interfaz web.
- administrar proveedores desde la interfaz web.
- administrar o descargar modelos de inteligencia artificial desde la
  interfaz web.

Esta decisión permite mantener controlada la relación entre los
identificadores públicos, los proveedores, los modelos técnicos y las
políticas de generación de código.

Una evolución futura podría incorporar mecanismos de configuración más
flexibles sin modificar el principio de que los modelos utilizados deben
estar previamente autorizados por ABAPCompass.

## 15.2 Proveedores de inteligencia artificial

La arquitectura de v0.3.0 mantendrá la abstracción `AIProvider` para
evitar que los casos de uso dependan de una implementación concreta.

La ejecución real prevista para esta versión utilizará
`OllamaAIProvider`.

La existencia de esta implementación no deberá interpretarse como una
restricción arquitectónica que impida utilizar otros proveedores en el
futuro.

Versiones posteriores podrán incorporar nuevas implementaciones de
`AIProvider` para acceder a proveedores externos o a otras plataformas de
inteligencia artificial.

La incorporación de un nuevo proveedor podrá requerir mecanismos
adicionales de configuración, autenticación, tratamiento de errores,
protección de credenciales y seguridad que deberán diseñarse cuando
exista una necesidad concreta.

## 15.3 Capacidades funcionales

v0.3.0 mantendrá las tres capacidades funcionales definidas para
ABAPCompass:

```text
Asistente SAP
Explicación ABAP
Revisión ABAP
```

La versión no pretende proporcionar un entorno completo de desarrollo
ABAP ni sustituir las herramientas disponibles en los sistemas SAP.

Entre otras funcionalidades, v0.3.0 no proporcionará:

- edición completa de proyectos ABAP.
- compilación de código ABAP.
- ejecución de código ABAP.
- depuración de programas ABAP.
- despliegue de objetos en sistemas SAP.
- análisis estático equivalente al proporcionado por herramientas
  especializadas del ecosistema SAP.
- conexión directa con un sistema SAP para validar las respuestas
  generadas.

Estas capacidades podrán evaluarse en futuras versiones únicamente
cuando resulten coherentes con la finalidad y arquitectura de ABAPCompass.

## 15.4 Limitaciones de las respuestas generadas

Las respuestas proporcionadas por los modelos de inteligencia artificial
no son deterministas ni garantizan corrección técnica.

Una respuesta puede contener:

- interpretaciones incorrectas.
- información incompleta.
- alucinaciones o afirmaciones no fundamentadas.
- código sintácticamente incorrecto.
- código que no compile.
- utilización de elementos no disponibles en una versión concreta de
  SAP.
- propuestas inadecuadas para las características de un sistema
  determinado.
- clasificaciones o conclusiones no justificadas.
- recomendaciones que requieran revisión adicional de seguridad,
  rendimiento o adecuación funcional.

ABAPCompass no puede garantizar la corrección técnica ni la adherencia
semántica del contenido generado por el modelo.

Las políticas `none`, `snippets` y `full` permiten establecer el
comportamiento solicitado respecto a la generación de código, pero las
instrucciones proporcionadas al modelo no garantizan por sí mismas su
cumplimiento.

Cuando la política sea `none`, ABAPCompass aplicará adicionalmente el
control determinista definido para v0.3.0. Este control eliminará los
bloques de código que puedan identificarse estructuralmente como tales
antes de exponer la respuesta.

El control no intentará identificar como código fragmentos incluidos
dentro del texto ordinario de la respuesta. Por tanto, contenido con
apariencia de código que no se encuentre estructuralmente delimitado
podrá permanecer en la respuesta.

Las políticas `snippets` y `full` no incorporarán este filtrado
determinista y dependerán de las instrucciones proporcionadas al modelo
para orientar la extensión del código generado.

Por estos motivos, las respuestas deberán permanecer sujetas a revisión
profesional antes de utilizar la información, ejecutar acciones
propuestas o emplear código generado en un entorno productivo.

## 15.5 Ausencia de integración directa con sistemas SAP

v0.3.0 no establecerá conexiones con sistemas SAP para obtener
información o ejecutar operaciones.

El contexto necesario para resolver una consulta deberá ser
proporcionado por el usuario mediante las capacidades disponibles.

ABAPCompass no podrá comprobar automáticamente aspectos dependientes de un
sistema concreto, como:

- objetos existentes.
- parametrización.
- versiones y componentes instalados.
- desarrollos propios.
- estructuras de datos específicas.
- autorizaciones.
- resultados de compilación o ejecución.

Una posible evolución futura podría estudiar mecanismos controlados de
integración con sistemas SAP.

Cualquier incorporación de este tipo requeriría una revisión específica
de arquitectura, seguridad, autenticación, autorizaciones y tratamiento
de la información.

## 15.6 Persistencia e historial

v0.3.0 no proporcionará persistencia de conversaciones ni un historial
permanente de las operaciones realizadas.

El estado necesario para la interacción de la interfaz se mantendrá
únicamente durante el uso de la aplicación según lo definido para esta
versión.

La selección del modelo tampoco requerirá persistencia permanente entre
sesiones.

Como consecuencia, una nueva sesión podrá comenzar nuevamente con el
modelo predeterminado indicado por la API.

Una evolución futura podrá incorporar persistencia de conversaciones
para recuperar el contexto de trabajos, consultas o proyectos de mayor
duración.

La introducción de almacenamiento permanente requerirá definir
previamente qué información debe conservarse, durante cuánto tiempo y
con qué medidas de protección.

## 15.7 Usuarios, autenticación y autorización

v0.3.0 no incorporará gestión de usuarios, autenticación ni
autorización.

La aplicación no diferenciará permisos ni capacidades en función de la
identidad del usuario.

Esta decisión es coherente con el alcance previsto y con la ausencia de
un despliegue productivo público definido para la versión.

Una evolución futura podrá incorporar autenticación y autorización
basadas en perfiles para restringir tanto el acceso a ABAPCompass como las
capacidades disponibles para cada usuario.

A modo de ejemplo, podrían contemplarse perfiles con diferentes niveles
de acceso, como:

- responsables de departamento o personal de IT con acceso autorizado a
  la aplicación.
- personal de soporte con acceso únicamente a capacidades de consulta.
- personal de IT con acceso a todas las capacidades disponibles.

Estos perfiles son únicamente ejemplos de una posible evolución y no
constituyen requisitos cerrados para una versión posterior.

La incorporación de autenticación y autorización requerirá definir el
modelo de identidad, los permisos, la protección de las sesiones y los
mecanismos de administración correspondientes.

## 15.8 Configuración de modelos

Las características asociadas a los modelos soportados serán definidas
por ABAPCompass.

El usuario podrá seleccionar un modelo disponible, pero no podrá
modificar directamente mediante la interfaz:

- el proveedor asociado.
- el identificador técnico utilizado por el proveedor.
- la política `codeSuggestionMode`.
- los parámetros internos de conexión.
- las credenciales.
- otros parámetros internos de ejecución.

Esta restricción mantiene controlada la configuración utilizada para
ejecutar las operaciones.

Versiones posteriores podrán permitir una configuración más flexible
cuando exista una necesidad concreta y puedan mantenerse los controles
necesarios para evitar configuraciones no autorizadas o inconsistentes.

## 15.9 Interfaz web

La interfaz de v0.3.0 estará orientada a proporcionar un medio sencillo
de interacción con las capacidades existentes de ABAPCompass.

No se pretende desarrollar en esta versión una plataforma web de
propósito general ni incorporar funcionalidades ajenas a las operaciones
definidas.

Entre otras posibilidades, no forman parte del alcance:

- personalización avanzada de la interfaz.
- gestión de cuentas de usuario.
- sincronización entre dispositivos.
- historial persistente de conversaciones.
- administración de modelos.
- administración de proveedores.
- paneles de administración.
- colaboración entre usuarios.

La interfaz podrá evolucionar progresivamente cuando nuevas
funcionalidades de ABAPCompass requieran mecanismos adicionales de
interacción.

## 15.10 Ejecución local y recursos disponibles

El funcionamiento con modelos locales estará condicionado por los
recursos disponibles en el equipo donde se ejecute el proveedor
correspondiente.

El rendimiento y los tiempos de respuesta podrán variar en función de:

- modelo utilizado.
- tamaño y características del modelo.
- recursos de CPU y memoria disponibles.
- utilización de aceleración por hardware.
- longitud de la entrada.
- longitud de la respuesta generada.
- carga existente en el equipo.

La selección de los modelos utilizados en v0.3.0 deberá ser compatible
con el entorno disponible para el desarrollo y las pruebas.

ABAPCompass no garantizará tiempos de respuesta equivalentes entre modelos
ni entre equipos con características diferentes.

La utilización futura de proveedores externos podría modificar estas
características de rendimiento, pero introduciría a su vez dependencias
de red, disponibilidad del servicio, costes y requisitos adicionales de
seguridad y privacidad.

## 15.11 Calidad de los modelos

Las capacidades observadas en ABAPCompass dependerán parcialmente de las
características del modelo seleccionado.

La existencia de varios modelos permitirá utilizar alternativas con
orientaciones y capacidades diferentes, pero no implica que todos
proporcionen la misma calidad para cualquier operación.

Las pruebas con modelos reales permitirán comprobar su comportamiento
dentro de los escenarios previstos para v0.3.0, sin constituir una
garantía general sobre cualquier consulta posible.

La evolución futura del catálogo podrá sustituir, incorporar o retirar
modelos cuando existan alternativas más adecuadas o cambien las
necesidades de la aplicación.

Estos cambios deberán realizarse manteniendo los contratos públicos y
las responsabilidades arquitectónicas definidas por ABAPCompass siempre que
resulte posible.

## 15.12 Evolución hacia nuevos proveedores

La separación entre `ModelCatalog`, `AIProviderResolver` y `AIProvider`
deberá facilitar la incorporación futura de proveedores adicionales.

Conceptualmente, una futura versión podría permitir:

```text
ModelCatalog
     |
     v
AIProviderResolver
     |
     +--> OllamaAIProvider
     |
     +--> ProveedorExternoAIProvider
     |
     +--> ...
```

La incorporación de nuevos proveedores no deberá requerir que los casos
de uso conozcan cuál de ellos ejecuta una operación.

Tampoco deberá requerir que la interfaz web conozca direcciones,
credenciales o detalles específicos de cada proveedor.

Esta evolución permitiría utilizar servicios externos además de modelos
ejecutados localmente, manteniendo la abstracción definida por
`AIProvider`.

La implementación de esta posibilidad queda fuera del alcance de
v0.3.0.

## 15.13 Evolución de las capacidades

La arquitectura permitirá estudiar nuevas capacidades funcionales sin
convertirlas en requisitos de la versión actual.

Entre las posibles líneas de evolución podrán considerarse:

- incorporación de nuevos proveedores de inteligencia artificial además
  de la ejecución local mediante Ollama.
- incorporación de mecanismos RAG sobre fuentes internas o externas de
  información especializada y controlada.
- persistencia de conversaciones para recuperar contexto en trabajos o
  proyectos de larga duración.
- autenticación y autorización por perfiles para controlar el acceso a
  ABAPCompass y a sus diferentes capacidades.
- nuevas operaciones de asistencia para profesionales SAP.
- ampliación de las capacidades de análisis de código ABAP.
- incorporación de contexto adicional para mejorar las respuestas.
- integración controlada con herramientas o servicios externos.
- mecanismos de comparación o evaluación de respuestas entre modelos.

La incorporación de RAG requerirá definir, entre otros aspectos, las
fuentes autorizadas, los mecanismos de indexación y recuperación, la
actualización de la información y el tratamiento seguro del contexto
recuperado.

La persistencia de conversaciones requerirá definir el modelo de datos,
el ciclo de vida de la información y los controles de acceso
correspondientes.

La incorporación de cualquiera de estas funcionalidades requerirá
definir previamente su alcance, contratos, impacto arquitectónico,
requisitos de seguridad y estrategia de pruebas.

## 15.14 Evolución de la seguridad

Las medidas de seguridad definidas para v0.3.0 corresponden al alcance y
forma de ejecución previstos para esta versión.

Cualquier evolución que implique:

- exposición pública de la aplicación.
- incorporación de autenticación y autorización.
- almacenamiento permanente de información.
- utilización de proveedores externos.
- incorporación de fuentes documentales mediante RAG.
- tratamiento de credenciales.
- integración con sistemas SAP.
- ejecución de código.
- acceso a información corporativa.

requerirá una nueva evaluación de riesgos y la incorporación de
controles adecuados al nuevo escenario.

Las decisiones de seguridad futuras deberán adoptarse en función del
contexto real de utilización y no asumirse automáticamente a partir de
las medidas definidas para v0.3.0.

## 15.15 Cierre del alcance de v0.3.0

Las limitaciones descritas en este capítulo forman parte del alcance
deliberadamente establecido para v0.3.0 y no deberán interpretarse como
funcionalidades incompletas.

La versión estará orientada a consolidar:

- selección dinámica entre modelos soportados.
- resolución controlada del proveedor correspondiente.
- políticas diferenciadas de generación de código.
- control determinista de los bloques de código cuando la política sea
  `none`.
- contratos REST adaptados a la selección de modelos y a los metadatos de
  política.
- aviso de validación profesional independiente del modelo.
- interfaz web para las capacidades de ABAPCompass.
- tratamiento del contenido procedente del usuario y de los modelos como
  contenido no confiable.
- representación segura del contenido en la interfaz web sin insertarlo
  como HTML interpretable.
- ausencia de ejecución de código o acciones propuestas por los modelos.
- pruebas automatizadas de las responsabilidades deterministas.
- validación manual de la integración con los modelos reales.
- integración de los nuevos componentes en los mecanismos de calidad y
  validación del proyecto.

Las posibles evoluciones descritas deberán abordarse, cuando
corresponda, como parte del diseño de versiones posteriores y no
ampliarán los criterios de aceptación establecidos para v0.3.0.
